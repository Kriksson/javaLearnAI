    # Задача №66 — Заявка на рейд с вложенной валидацией

**Сложность:** мини-проект, базовый Spring Boot.

**Закрепи:** проектирование Spring MVC API, DTO и модели ответа, Bean Validation, обработку состояния в памяти и интеграционные тесты `MockMvc`.

**Новая тема:** каскадная проверка вложенных объектов в JSON.

## Материал: `@Valid` на вложенном объекте

`@Valid` на аргументе контроллера проверяет поля самого запроса. Чтобы проверялись поля вложенного объекта, пометь его компонент `@Valid`.

`MapPointRequest.java`:

```java
import jakarta.validation.Valid;
import jakarta.validation.constraints.NotNull;

public record MapPointRequest(@NotNull @Valid Coordinates coordinates) {
}
```

`Coordinates.java`:

```java
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;

public record Coordinates(
        @Min(0) @Max(100) int x,
        @Min(0) @Max(100) int y) {
}
```

- `@Valid` на `coordinates` запускает проверки полей `Coordinates`.
- `@NotNull` отдельно запрещает отсутствующий объект: каскадная проверка сама по себе пропускает `null`.
- Пример относится к координатам карты и не является решением заявки на рейд.

## Проект

Спроектируй и реализуй API регистрации игроков на рейд. Заявка содержит имя игрока и вложенный профиль героя. Самостоятельно выбери модели и структуру компонентов; фиксированы только правила данных и HTTP-контракт.

### Правила данных

- `playerName`: от 1 до 30 непробельных символов.
- Объект `hero` обязателен.
- `hero.name`: от 1 до 40 непробельных символов.
- `hero.level`: от 1 до 100 включительно.
- `hero.className`: от 1 до 20 непробельных символов.
- Каждая заявка получает уникальный положительный ID; одинаковые ID невозможны.
- ID хранится как `long`.
- Хранилище работает в памяти и очищается после перезапуска; база данных и SQL не используются.

### HTTP-контракт

- `POST /guild/raid-signups` принимает JSON:

  ```json
  {"playerName":"Кирилл","hero":{"name":"Лира","level":25,"className":"mage"}}
  ```

  Возвращает `201 Created`, `Location: /guild/raid-signups/{id}` и JSON с `id`, `playerName` и вложенным объектом `hero`.
- `GET /guild/raid-signups/{id}` возвращает `200` и сохранённую заявку.
- Неизвестный ID, который помещается в `long` (включая `0` и отрицательные значения), возвращает `404` без тела.
- Нечисловой ID и число вне диапазона `long` возвращают `400`.
- Пустые, отсутствующие, слишком длинные или выходящие за границы поля, отсутствующий `hero` и синтаксически неверный JSON возвращают `400`.
- Строки из пробелов считаются пустыми.

### Пример ответа

```json
{
  "id": 1,
  "playerName": "Кирилл",
  "hero": {"name":"Лира","level":25,"className":"mage"}
}
```

Ещё два случая:

- `GET /guild/raid-signups/1` для сохранённой заявки возвращает `200` и такой же JSON с ID `1`.
- `POST /guild/raid-signups` с `{"playerName":"Кирилл","hero":{"name":"Лира","level":0,"className":"mage"}}` возвращает `400`.

## Самостоятельное проектирование

- Сам выбери DTO, модель ответа, хранение в памяти и разбиение логики на компоненты.
- Реализуй каскадную валидацию вложенного профиля через `@Valid`, а обязательность `hero` проверь отдельно через `@NotNull`.
- Размещай самостоятельные модели и компоненты в отдельных `.java`-файлах; не вкладывай доменные классы в контроллер.
- Сохрани заданные маршруты, поля JSON, ограничения, статусы и поведение `Location`.

## Критерии готовности

- `@Valid` на `hero` запускает ограничения вложенного профиля; одного `@Valid` на аргументе контроллера недостаточно.
- `@NotNull` на `hero` отклоняет отсутствующий или `null` объект.
- Тесты проверяют создание и `Location`, чтение, неизвестный и некорректный ID, повторные выдачи уникальных ID, допустимые границы и ошибки валидации на верхнем и вложенном уровнях, включая пробельные строки и отсутствующие поля.
- Используй подключённые зависимости; добавлять библиотеки не нужно.
