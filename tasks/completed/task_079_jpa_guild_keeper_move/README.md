# Задача №79 — Перевод хранителя в другую гильдию

**Сложность: базовая. Следующий шаг после чтения JPA-связей.**

Теперь хранитель может перейти в другую существующую гильдию. Самостоятельно спроектируй и собери приложение с нуля в пакете `learning.task079`. Имена Java-классов, полей и методов выбираешь сам. Тренер предоставляет условие и тесты; исходные файлы и конфигурацию создаёшь ты.

Закрепляем: две сущности, `@ManyToOne`, `@JoinColumn`, репозитории нужного типа, `findById`, `@Service`, `@Transactional`, JSON-запрос, валидацию, `PUT` и HTTP-статусы.

Новый материал: **managed entity и dirty checking** — отслеживание и сохранение изменений загруженной сущности внутри транзакции. Никаких новых зависимостей сверх знакомого Spring Boot / JPA не требуется.

## Как Hibernate сохраняет изменение

В задачах №76–78 ты получал сущности и читал их поля. Здесь нужно изменить связь у существующей сущности.

Если Spring-сервис начинает транзакцию через `@Transactional` и внутри неё вызывает `repository.findById(...)`, Hibernate загружает объект и отслеживает его в persistence context — наборе управляемых сущностей текущей работы с БД. Такой объект называется **managed entity**.

Обычный метод сущности, например setter, меняет поле Java-объекта. При синхронизации с БД перед успешным завершением транзакции Hibernate обнаруживает изменение — **dirty checking** — и выполняет SQL `UPDATE`. Явный `save()` для этой уже загруженной и управляемой сущности в этой практике не нужен. Изменение DTO или отдельно созданного через `new` объекта само по себе такого эффекта не даёт.

Для связи хранитель → гильдия новое значение Java-поля должно быть объектом существующей гильдии. Hibernate переведёт это изменение в новое значение `guild_id`. Имя, уровень и ID хранителя при этом сохраняются.

`@Transactional` поставь на публичный метод отдельного Spring-сервиса либо на сам сервис. Контроллер вызывает внедрённый сервис; Spring открывает транзакцию перед вызовом и завершает её после возвращения метода. Не создавай сервис через `new` и не рассчитывай на вызов аннотированного метода из другого метода того же объекта. Для этой операции транзакция должна допускать запись: без `readOnly = true`.

[Транзакции Spring Data JPA](https://docs.spring.io/spring-data/jpa/reference/3.5/jpa/transactions.html), [вызов методов с `@Transactional`](https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/declarative/annotations.html).

### Отдельный работающий пример: переименование книги

Пример компилируется в Spring Boot JPA приложении, где пакет `example.books` сканируется. Он остаётся в учебном материале; не размещай его в файлах решения.

`Book.java`:

```java
package example.books;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

@Entity
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String title;

    protected Book() {}

    public Book(String title) {
        this.title = title;
    }

    public void rename(String title) {
        this.title = title;
    }
}
```

`@Entity` делает книгу JPA-сущностью. `@Id` обозначает идентификатор, `IDENTITY` получает его от базы. Пустой конструктор нужен Hibernate. `rename` — обычный Java-метод, меняющий поле; он сам не выполняет SQL.

`BookRepository.java`:

```java
package example.books;

import org.springframework.data.jpa.repository.JpaRepository;

public interface BookRepository extends JpaRepository<Book, Long> {}
```

Репозиторий работает с книгами и ID типа `Long`; реализацию `findById` предоставляет Spring Data.

`BookService.java`:

```java
package example.books;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class BookService {
    private final BookRepository repository;

    public BookService(BookRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public void rename(long id, String title) {
        Book book = repository.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("Book not found"));
        book.rename(title);
    }
}
```

- `@Service` регистрирует компонент; конструктор получает репозиторий от Spring.
- `@Transactional` объединяет загрузку и изменение в одной транзакции.
- `findById` возвращает управляемую книгу; `orElseThrow` прекращает операцию, если книги нет.
- `book.rename(title)` меняет объект. После успешного выхода из метода Hibernate сохраняет новое название. Здесь нет `save()`.

Предположим, строка книги `id=7` содержит название `Old`. Вызов внедрённого сервиса `bookService.rename(7, "New")` завершится сохранением `New` в БД.

Полный путь данных для такого API: JSON `{"title":"New"}` → Spring/Jackson создаёт DTO из `@RequestBody` → контроллер проверяет входные данные → вызывает внедрённый сервис → Spring открывает транзакцию → репозиторий загружает книгу → код меняет поле → Hibernate обнаруживает изменение и выполняет `UPDATE` → транзакция фиксируется → контроллер возвращает успешный HTTP-ответ. Проверки отсутствующего, пустого и слишком длинного названия пишет разработчик либо задаёт через Bean Validation; пример сервиса предполагает уже проверенное название.

## Модель и настройка

Используй H2 в памяти. Вручную создай `src/main/resources/application.properties`: URL начинается с `jdbc:h2:mem:`, пользователь `sa`, пустой пароль, `spring.jpa.hibernate.ddl-auto=create-drop`. Hibernate создаёт пустые таблицы. Не добавляй начальные данные, `schema.sql` или `data.sql`.

Создай отдельные сущности гильдии и хранителя. Явно отобрази таблицы через `@Table`, колонки через `@Column`; связь — через `@ManyToOne` и `@JoinColumn(name = "guild_id", nullable = false)`. Обратная коллекция `@OneToMany` здесь не нужна и не используется.

| Таблица | Колонки |
|---|---|
| `guilds` | `id BIGINT` — identity primary key; `name VARCHAR(40) NOT NULL` |
| `guild_keepers` | `id BIGINT` — identity primary key; `name VARCHAR(40) NOT NULL`; `level INTEGER NOT NULL`; `guild_id BIGINT NOT NULL` — внешний ключ на `guilds.id` |

У хранителя должна быть возможность поменять ссылку на гильдию обычным Java-методом. Имя этого метода выбираешь сам.

## HTTP-контракт

```http
PUT /keepers/{keeperId}/guild
Content-Type: application/json

{"guildId":12}
```

- `keeperId` — ID существующего хранителя типа `long`.
- JSON содержит `guildId` — положительный ID целевой гильдии в диапазоне `long`. В DTO используй `Long`, чтобы различать отсутствующее значение и число. Допустимы ID больше `Integer.MAX_VALUE`, включая `Long.MAX_VALUE` у целевой гильдии.
- Существуют хранитель и целевая гильдия → `204 No Content` без тела. В БД меняется только `guild_id` выбранного хранителя.
- Имя, уровень и собственный ID хранителя, все остальные хранители и все гильдии остаются прежними. Допустимы уровень `0` и `Integer.MAX_VALUE`, имена длиной 40 символов, кириллица и кавычки.
- Хранитель уже принадлежит целевой гильдии → также `204`. Повторный одинаковый запрос не создаёт новых строк и не меняет результат.
- После успешного перевода можно тем же API перевести хранителя обратно либо в другую гильдию; используется актуальная запись из БД.
- При корректном JSON неизвестный хранитель или неизвестная целевая гильдия → `404`. Существующие строки не изменяются, новые не создаются. Отсутствие обоих ресурсов также даёт `404`.
- Для существующего хранителя отсутствующее тело, JSON `null`, отсутствующий или `null` `guildId`, значение `0` или отрицательное → `400`.
- Повреждённый JSON, непреобразуемое в `Long` значение `guildId` или число вне диапазона `long` → `400` без изменений БД.
- Формат тела ошибки свободный.
- База отклоняет хранителя без гильдии либо со ссылкой на несуществующую гильдию.

Spring/Jackson разбирает JSON и преобразует `guildId` в `Long`. Обязательность и положительность ID проверяешь ты — вручную или через Bean Validation. Сервис ищет хранителя через репозиторий хранителей, гильдию — через репозиторий гильдий; сначала проверяет наличие обоих ресурсов, затем меняет связь. Контроллер переводит результат или исключение сервиса в указанный статус.

## Ограничения реализации

- Операция выполняется в отдельном `@Service` через публичный метод с `@Transactional`, допускающей запись. Контроллер вызывает сервис через внедрённую зависимость.
- Обе существующие сущности загружаются через `JpaRepository.findById` внутри этой транзакции.
- Меняй связь у **загруженного хранителя**, передавая объект найденной гильдии. Сохранение обеспечивает dirty checking.
- Для этой операции не вызывай `save`, `saveAndFlush`, `saveAll`, `flush`, `EntityManager.persist` или `merge`; не создавай новую сущность взамен существующей. Этот запрет помогает увидеть работу dirty checking, а не задаёт универсальное правило для всех JPA-приложений.
- Не используй `JdbcTemplate`, ручной SQL, `@Query` / `@Modifying` или `findAll()` в приложении. Тесты используют JDBC для независимой подготовки и проверки БД.
- Тесты выполняются без транзакции вокруг тестового метода и отключают `spring.jpa.open-in-view`: загрузка и изменение должны работать за счёт транзакции твоего сервиса.
- Использование нужных компонентов и ограничения сохранения дополнительно проверяются при просмотре решения.

## Примеры

Пусть хранитель `4` принадлежит гильдии `3`; гильдия `12` существует.

1. `PUT /keepers/4/guild` с `{"guildId":12}` → `204`; теперь у хранителя `4` в БД `guild_id=12`, остальные поля прежние.
2. Повтор того же запроса → `204`; новых строк нет. Запрос с `{"guildId":3}` → `204`, хранитель возвращается в гильдию `3`.
3. Запрос с `{"guildId":99}` → `404`, если гильдии `99` нет; прежняя связь сохраняется. Запрос с `{"guildId":null}` → `400`.
