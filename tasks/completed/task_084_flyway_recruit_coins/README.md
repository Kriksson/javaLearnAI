# Задача №84 — Миграция V2: монеты существующих рекрутов

**Сложность: базовая. Обновление схемы с сохранением данных.**

У гильдии уже есть база версии V1 и сохранённые рекруты. Теперь каждому рекруту нужен запас монет. Собери приложение с нуля в пакете `learning.task084` и добавь колонку новой миграцией V2. Старые рекруты должны остаться с прежними ID, именами и уровнями; начальный запас монет — 0.

Закрепляем: Flyway, PostgreSQL, JPA, identity ID, DTO, валидацию, внешний конфиг и Hibernate `validate`.

Новые понятия: **переход существующей базы с V1 на V2** и **DEFAULT при добавлении колонки и вставке строки**.

## Как развивать схему

Применённую V1 сохраняют. Следующее изменение оформляют файлом V2: Flyway видит историю конкретной базы и выполняет только отсутствующие версии. На пустой базе выполняются V1 и V2; на базе с V1 выполняется V2; на базе с обеими версиями повторное применение не требуется. [Порядок и история миграций](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/versioned-migrations).

Перенеси в новую задачу свою V1 из архива №83 **без редактирования**:

`tasks/completed/task_083_flyway_recruit_schema/src/main/resources/db/migration/V1__create_recruits.sql`.

Её рабочее место остаётся `src/main/resources/db/migration/V1__create_recruits.sql`. Тесты проверяют контрольную сумму Flyway. Не добавляй новую колонку в V1: эту работу выполняет V2.

### Отдельный работающий пример: количество экземпляров книги

В другой базе уже существует `books` с колонками `id`, `title` и сохранёнными книгами. Файл `V2__add_book_copies.sql` может содержать:

```sql
ALTER TABLE books
    ADD COLUMN copies INTEGER NOT NULL DEFAULT 1 CHECK (copies >= 0);
```

- `ALTER TABLE books` изменяет существующую таблицу и сохраняет её строки.
- `ADD COLUMN` добавляет колонку.
- `DEFAULT 1` даёт существующим книгам значение 1; оно также используется для новой строки, если колонка пропущена в INSERT.
- `NOT NULL` запрещает `NULL`, `CHECK` отклоняет отрицательное количество.

Например, после миграции SQL `INSERT INTO books (title) VALUES ('Atlas')` сохранит `copies=1`, если `id` выдаётся identity-колонкой. Явное `copies=NULL` отклоняется: DEFAULT используется при пропуске колонки или SQL-ключевом слове `DEFAULT`. [Добавление колонок PostgreSQL](https://www.postgresql.org/docs/current/ddl-alter.html#DDL-ALTER-ADDING-A-COLUMN), [значения по умолчанию в INSERT](https://www.postgresql.org/docs/current/sql-insert.html).

Для JPA-сущности книги начальное значение Java-поля можно задать отдельно:

```java
private int copies = 1;
```

Эта строка устанавливает количество в новом Java-объекте. При `save` Hibernate может включать поле в INSERT, поэтому продумай начальное значение в своей сущности: SQL DEFAULT и значение Java-поля участвуют на разных шагах. Эти примеры остаются в условии; миграцию и модель рекрута пишешь сам.

Полный путь:

```text
База с V1 и рекрутами → старт приложения → Flyway выполняет V2
                     → старая таблица получает coins, старые строки имеют coins=0
                     → Hibernate validate проверяет обновлённую сущность
GET → findById → Hibernate читает четыре колонки → DTO с coins
POST JSON → Spring/Jackson создаёт DTO запроса → твоя валидация
          → новая сущность с coins=0 → save → INSERT → DTO и Location
```

## Миграции и схема

Нужны ровно две SQL-миграции в стандартном каталоге `src/main/resources/db/migration/`:

1. `V1__create_recruits.sql` — прежний файл №83, неизменный.
2. `V2__add_recruit_coins.sql` — самостоятельно написанное изменение существующей таблицы.

После V2 в `recruits` ровно четыре колонки:

| Колонка | Требования |
|---|---|
| `id` | Прежний `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `name` | Прежний `VARCHAR(40) NOT NULL` |
| `level` | Прежний `INTEGER NOT NULL CHECK (level >= 0)` |
| `coins` | `INTEGER NOT NULL`, DEFAULT 0, CHECK `coins >= 0` |

Сохрани существующую таблицу, её ID и значения имени/уровня, генерацию ID и запись истории V1. Все старые строки получают `coins=0`. Не удаляй и не пересоздавай таблицу, не очищай и не заменяй строки, не сбрасывай последовательность ID. V2 не добавляет рекрутов. Другие таблицы приложения не нужны; историю создаёт Flyway.

Создай JPA-сущность с явными именами таблицы и колонок, ID типа `Long` с `GenerationType.IDENTITY` и целочисленным количеством монет. Новая сущность для POST должна сохраняться с `coins=0`. Читай и сохраняй через Spring Data JPA. Имена классов и внутренних методов выбираешь сам.

## HTTP-контракт

### POST /recruits

Тело по-прежнему содержит имя и уровень: `{"name":"Mira","level":3}`. Пользователь не задаёт начальный запас монет.

- `name` обязателен, не `null`, не пуст и не состоит только из пробелов, максимум 40 символов. Сохраняй допустимое имя точно, включая кириллицу, кавычки и пробелы вокруг непустого имени.
- `level` обязателен и не `null`, от 0 до `Integer.MAX_VALUE`; входной DTO различает отсутствующее значение и ноль.
- Корректный запрос → `201 Created`, `Location: /recruits/{выданныйId}`, JSON с ровно четырьмя полями: `id`, `name`, `level`, `coins`. ID положительный и выдан PostgreSQL; `coins` равен 0 в ответе и базе.
- Повтор одинакового POST создаёт другую строку с другим ID, сохраняя прежние.
- Отсутствующее тело, JSON `null`, отсутствующее или `null` поле, недопустимое имя, отрицательный уровень, повреждённый JSON, непреобразуемый уровень или число вне диапазона `int` → `400` без новой записи и изменений существующих. Формат ошибки свободный.

### GET /recruits/{id}

- ID имеет диапазон `long`, поддерживай значения больше `Integer.MAX_VALUE`.
- Существующая строка → `200`, DTO с ровно `id`, `name`, `level`, `coins`; отсутствующий или удалённый ID → `404`.
- Читай актуальные имя, уровень и монеты из PostgreSQL: внешние изменения отражаются в следующем GET. Монеты могут быть от 0 до `Integer.MAX_VALUE`.
- GET не меняет строки; сущность напрямую в HTTP-ответ не возвращай. Endpoint для изменения монет в этой задаче не требуется.

### Ограничения и повторные запуски

База отклоняет `NULL` в имени, уровне и монетах, имя длиннее 40 символов, отрицательные уровень или монеты. INSERT без `coins` сохраняет 0. После повторного открытия контекстов рекруты и их значения сохраняются, обе записи истории миграций остаются неизменными. Hibernate с `validate` отклоняет схему с отсутствующей ожидаемой колонкой и не восстанавливает её.

Сам создавай Java-файлы в `src/main/java/learning/task084/`: стартовый класс, сущность, репозиторий, контроллер, DTO запроса и ответа; сервис добавляй по необходимости. Каждый самостоятельный класс — отдельный файл. Вручную создай конфигурацию, перенеси неизменную V1 и напиши V2. Проверь необходимые зависимости и сборку; Java остаётся 21.

В `src/main/resources/application.properties`:

| Свойство | Значение |
|---|---|

Используй стандартную автоконфигурацию Flyway с тем же DataSource, стандартными расположением миграций и названием истории. Фиксированные схемы и отдельное подключение Flyway не задавай. Не используй H2, `schema.sql`, `data.sql`, `import.sql`, ручное создание таблиц из Java, `baseline-on-migrate`, очистку схемы или `repair` для обхода изменённой V1. Доступ к рекрутам из приложения — через JPA; SQL допустим в миграциях. `JdbcTemplate`, `@Query` и локальные коллекции для хранения рекрутов в приложении не используются.

Для обычного запуска можно указать свою учебную базу №83 с применённой V1 или новую пустую учебную базу. База №82 без истории Flyway для этого сценария не подходит. Подключение, права и переменные окружения задаёшь сам.

## Примеры

1. В базе V1 есть рекрут `{"id":12,"name":"Mira","level":3}`. После старта приложения с V2 GET `/recruits/12` → `200` и `{"id":12,"name":"Mira","level":3,"coins":0}`.
2. POST `{"name":"Rin","level":0}` → `201`, например `Location: /recruits/13` и `{"id":13,"name":"Rin","level":0,"coins":0}`. Если клиент БД изменит монеты этой строки на 5, следующий GET вернёт `coins: 5`.
3. Повторный старт → обе версии уже применены, прежние монеты сохранены. POST с отрицательным уровнем → `400`; прямой INSERT с отрицательными монетами отклоняет CHECK.
