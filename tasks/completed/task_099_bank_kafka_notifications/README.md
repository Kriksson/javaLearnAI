## 1. Зачем нужен брокер

Раньше контроллер вызывал сервис и получал результат прямо в HTTP-запросе. Теперь отправитель оставляет событие в Kafka, а обработчик читает его независимо. Kafka — отдельный процесс, который хранит поток записей. Отправитель и обработчик в этой практике находятся в одном Spring-приложении, но передают данные через настоящий брокер.

В учебном банке оператор создаёт уведомление для клиента. API подтверждает публикацию в Kafka. Listener позже читает событие и добавляет уведомление в список обработанных. GET позволяет увидеть результат обработки; фактической отправки SMS или email нет.

```text
POST JSON → Bean Validation → JSON-строка → KafkaTemplate → Kafka
                                                           ↓
GET JSON ← список обработанных ← разбор JSON ← @KafkaListener
```

POST отвечает `202 Accepted` после подтверждения отправки брокером. Это ещё не подтверждение работы listener. При быстром обработчике уведомление может попасть в список даже до получения HTTP-ответа; обязательной задержки нет.

## 2. Минимум терминов

| Понятие | Смысл в этой задаче |
|---|---|
| Broker | Запущенный сервер Kafka; в тестах его запускает Docker через Testcontainers |
| Topic | Именованный поток записей: `bank.notifications.v1` |
| Record | Одна запись: ключ, значение и служебные данные Kafka |
| Producer | Отправляет запись в topic; в Spring используем `KafkaTemplate` |
| Consumer | Читает записи; метод с `@KafkaListener` получает их значение |
| Partition | Упорядоченная часть topic. Здесь она одна: порядок последовательных записей сохраняется |
| Offset | Номер позиции записи внутри partition. Позже отдельно изучим сохранение позиции и повторное чтение |
| Consumer group | Группа обработчиков с общим прогрессом чтения. Здесь имя `bank-notifications-v1`, обработчик один |

Ключ записи — строковое представление `clientId`. При нескольких partitions ключ обычно помогает направлять связанные события в одну partition. Здесь распределение не изучаем: partition всего одна. Разные группы читают поток независимо; внутри одной группы partition распределяются между consumer. Масштабирование проверим отдельно.

## 4. Внешний контракт

### Публикация уведомления

`POST /api/notifications`, `Content-Type: application/json`:

```json
{"clientId": 17, "text": "Карта готова"}
```

Требования:

- `clientId` — обязательное целое число типа `long`, от `1` до `Long.MAX_VALUE`; используй nullable-тип в DTO, чтобы отличать отсутствие значения от нуля.
- `text` — обязательная строка, не `null`, не пустая и не состоящая только из пробельных символов; длина от 1 до 120 включительно по `String.length()`.
- Сохраняй текст без обрезания пробелов и других изменений, включая кириллицу, кавычки и перевод строки.
- Успех: `202 Accepted` с пустым телом после успешного подтверждения отправки Kafka. Не ограничивайся вызовом `send()` без обработки результата: он возвращает `CompletableFuture`. Для первого шага допустимо ограниченное ожидание `get(timeout, unit)`, как в примере. Успешный ответ при ошибке отправки недопустим; точный формат ошибки брокера в этом шаге не фиксируется.
- Отсутствующие/некорректные значения по указанным ограничениям, пустое тело и синтаксически сломанный JSON дают `400`. При таком ответе запись в topic не появляется. Формат тела ошибки свободный.
- POST публикует ровно одну запись и **не добавляет уведомление в список обработанных**. Список меняет только listener.

Контракт записи в Kafka:

| Часть | Значение |
|---|---|
| Topic | `bank.notifications.v1` |
| Key | Строка `"17"`, полученная из `clientId` |
| Value | JSON-объект ровно с полями `clientId` и `text`, например `{"clientId":17,"text":"Карта готова"}` |
| Передача | Ключ и значение передаются как строки через `StringSerializer` / `StringDeserializer` |

Порядок полей и пробелы между JSON-токенами не важны. `ObjectMapper.writeValueAsString(...)` преобразует объект в JSON-строку; `readValue(...)` выполняет обратное преобразование в listener. Не собирай JSON конкатенацией: кавычки и переводы строк требуют экранирования.

### Чтение обработанных уведомлений

`GET /api/notifications?clientId=17`:

```json
[
  {"clientId": 17, "text": "Карта готова"}
]
```

- Ответ — `200` и JSON-массив уведомлений только запрошенного клиента, каждое с полями `clientId` и `text`.
- Неизвестный клиент: `200` и `[]`.
- Если listener ещё не обработал событие, уведомления в ответе пока нет. Проверка повторяет GET в пределах ограниченного времени.
- Несколько последовательно отправленных событий одного клиента возвращаются в порядке чтения из единственной partition.
- `clientId` обязателен; пустое значение, ноль, отрицательное число, нечисловая строка или выход за диапазон `long` дают `400`.

Список хранится только в памяти текущего запуска. HTTP-поток читает его одновременно с записью из listener: выбери потокобезопасную коллекцию или синхронизацию и возвращай безопасный снимок. Восстановление списка после перезапуска и очистка старых данных пока не требуются. Повторные события пока не объединяются; гарантии exactly-once здесь нет.

### Настройка Kafka

- Адрес получай из `spring.kafka.bootstrap-servers`, без жёстко заданного порта в Java-коде. В тестах свойство переопределяет `@DynamicPropertySource`.
- При старте приложение создаёт topic через Spring bean типа `NewTopic`: одна partition и replication factor `1`. `TopicBuilder` показан в примере. Автоматическое создание topic на брокере в тестах отключено.
- Listener использует group id `bank-notifications-v1`; его можно указать в настройках или аннотации.
- Для новой группы задай `auto-offset-reset=earliest`, чтобы прочитать уже опубликованные записи. Это выбор начальной позиции при отсутствии сохранённого offset, а не команда перечитывать весь topic при каждом запуске.
- Producer и consumer используют строковые сериализаторы/десериализаторы для key и value. Работа с JSON остаётся явной в коде приложения.
- Используй `KafkaTemplate` и `@KafkaListener`; подменять Kafka внутренней очередью, прямым вызовом listener или mock нельзя.
- Ручные ack, собственный poll-loop и собственная фабрика consumer в этой задаче не нужны: достаточно автоконфигурации Boot.

## 5. Три примера поведения

1. POST для клиента `17` с текстом «Карта готова» → `202`. После обработки listener GET для `17` содержит уведомление; GET для `18` возвращает `[]`.
2. POST с `{"clientId":17,"text":"   "}` → `400`, новая запись в Kafka не появляется.
3. Корректная запись опубликована в topic независимым producer без HTTP → listener обрабатывает её; GET возвращает уведомление. Поэтому недостаточно записывать данные только в POST.
