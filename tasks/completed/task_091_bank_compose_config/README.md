# №91 — Банк: запуск API через Docker Compose

Сложность: **базовая**. Создаёшь приложение с нуля в `learning.task091`; внутренние имена классов и методов выбираешь сам. Решение №90 сохранено в архиве, его рабочие файлы освобождены.

Закрепляем: Spring Boot REST, DTO, внешнюю конфигурацию, исполняемый JAR, Dockerfile, публикацию порта и отличие образа от контейнера.

Впервые: **Docker Compose** и **подстановка настроек из файла окружения**. Здесь один сервис; PostgreSQL, сеть между сервисами, volumes и healthcheck вводим следующими отдельными практиками.

## Сценарий и назначение

Команда банка запускает информационное API сервиса переводов в разных регионах. Раньше запуск требовал длинной команды `docker run`. Теперь описание сборки, порта и окружения хранится в `compose.yaml`, а значения конкретного запуска можно менять в `.env`.

Compose управляет контейнерами Docker по YAML-файлу. Он полезен и для одного сервиса; позже добавим в тот же файл базу. **Сервис Compose** — описание запуска контейнера; это другое понятие, чем Java-класс с `@Service`.

YAML использует отступы пробелами: вложенный блок относится к строке над ним. Удобно использовать два пробела; табуляцию не используй. `services` обозначает блок сервисов, `build` — сборку своего образа через Dockerfile, `ports` — публикацию портов, `environment` — переменные внутри контейнера. [Модель Compose](https://docs.docker.com/compose/intro/compose-application-model/).

## Отдельный работающий пример

Пример собирает свой образ со статической страницей и показывает передачу переменной. Он не содержит банковского API и остаётся в материале. Создай его в отдельной папке `site-demo`.

`index.html` примера:

```html
<!doctype html>
<html lang="en"><body><h1>Demo page</h1></body></html>
```

`Dockerfile` примера:

```dockerfile
FROM docker.io/library/nginx:stable-alpine
COPY index.html /usr/share/nginx/html/index.html
```

`FROM` берёт образ с готовым веб-сервером. `COPY` кладёт нашу страницу в образ. При запуске веб-сервер отдаёт её на порту 80. Исходный `index.html` после сборки для работы контейнера не требуется.

`compose.yaml` **примера**:

```yaml
services:
  preview:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "127.0.0.1:${DEMO_PORT:-8092}:80"
    environment:
      DISPLAY_NAME: "${DEMO_NAME-Guest}"
```

- `preview` — имя сервиса для команд Compose.
- `build` поручает Compose собрать собственный образ.
- `context: .` делает папку с compose.yaml контекстом сборки; Dockerfile может брать из неё файлы через `COPY`.
- `dockerfile: Dockerfile` выбирает файл с инструкциями сборки внутри контекста.
- `ports` связывает порт компьютера с портом 80 контейнера.
- `${DEMO_PORT:-8092}` подставляет порт; при отсутствующем или пустом значении использует 8092.
- `environment` явно передаёт значение контейнеру. `${DEMO_NAME-Guest}` использует `Guest` только при отсутствии переменной; пустая строка сохраняется.

Создай `.env` в папке примера:

```dotenv
DEMO_PORT=8092
DEMO_NAME=alex
```

Выполни:

```shell
docker compose config
docker compose up -d --build
curl http://localhost:8092
docker compose exec preview printenv DISPLAY_NAME
docker compose down
```

`config` покажет итоговое описание с подставленными значениями. `up -d --build` сначала соберёт образ по Dockerfile, затем создаст и запустит контейнер в фоне. `curl` получит страницу с текстом `Demo page`, `printenv` выведет `alex`. Nginx здесь не использует `DISPLAY_NAME` для страницы: переменную отдельно читает команда внутри контейнера.

Путь настройки: `.env` → Compose подставляет `DEMO_NAME` → `environment` создаёт `DISPLAY_NAME` в контейнере → `printenv` читает значение → видим `alex`.

**`.env` сам по себе не передаёт все свои строки контейнеру.** Он даёт значения для подстановки; для передачи нужна запись в `environment`. Если переменная есть и в `.env`, и в окружении терминала, побеждает терминал. `--env-file путь` выбирает другой файл вместо стандартного `.env`. [Подстановка и приоритет переменных](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/).

В твоём приложении путь такой: `.env` → Compose → `BANK_REGION` внутри контейнера → конфигурация Spring → контроллер → DTO → JSON. Чтение настройки в Spring реализуешь сам знакомым способом; разбирать `.env` в Java не нужно.

## Подробный разбор требований compose.yaml

### 1. Один сервис и его имя

В примере `services` — список описаний контейнеров, а `preview` — имя единственного сервиса. Все поля с большим отступом под `preview` относятся к нему. Список портов не является списком сервисов.

```yaml
services:
  preview:
    build:
      context: .
```

В задании назови этот сервис **api**, чтобы команда `docker compose logs api` и автоматические тесты обращались к нужному контейнеру. Это имя не связано с именем Java-контроллера или пакета.

### 2. build, context и Dockerfile

Dockerfile отвечает на вопрос «что положить в образ и как запускать приложение?». `compose.yaml` — «как собрать этот образ и с какими настройками создать контейнер?». Compose не заменяет Dockerfile.

```yaml
build:
  context: .
  dockerfile: Dockerfile
```

`context` задаёт папку файлов, доступных для сборки. Для этого примера точка означает `site-demo`, где лежит compose.yaml. `dockerfile` — путь к файлу инструкций относительно контекста. Сначала Compose находит Dockerfile, затем Docker выполняет его инструкции; `COPY index.html ...` читает страницу из контекста. `.dockerignore`, если он есть, исключает файлы из этого набора. [Контекст и Dockerfile в Compose](https://docs.docker.com/reference/compose-file/build/).

В задании точка означает корень `javaLearnAI`, поэтому инструкция Dockerfile сможет читать `target/bank-service.jar`. **Compose сам не запускает Maven**: в этой практике сначала собираешь JAR, затем выполняешь `docker compose up -d --build`.

`image` задаёт имя образа. В этой практике строка `image` не нужна: Compose назначает имя собранному образу из имени проекта и сервиса. Например, для проекта `site-demo` и сервиса `preview` это `site-demo-preview`. В Dockerfile строка `FROM` при этом остаётся: она задаёт базовый образ для сборки, это другая настройка. [Именование собранного образа](https://docs.docker.com/reference/cli/docker/compose/build/).

### 3. Имя проекта и container_name

Проект Compose объединяет созданные ресурсы одного запуска. По умолчанию его имя обычно берётся из имени папки с compose.yaml. Его можно явно задать в команде:

```shell
docker compose -p sandbox up -d --build
```

Для сервиса `preview` контейнер обычно получит имя `sandbox-preview-1`: проект, сервис и номер экземпляра. **Имя сервиса и имя контейнера — разные вещи.** В командах Compose обращайся к сервису: `docker compose -p sandbox logs preview`.

`container_name` закрепил бы одно имя контейнера независимо от проекта. Два запуска с таким именем конфликтовали бы. Поэтому в задании это поле просто не добавляй: тесты задают собственное имя проекта через `-p` и не должны пересекаться с твоим запуском. При параллельном запуске разным проектам нужны также разные опубликованные порты компьютера. [Имя проекта Compose](https://docs.docker.com/compose/how-tos/project-name/).

### 4. Публикация порта и значение 0

У короткой записи три части:

```text
адрес_компьютера:порт_компьютера:порт_контейнера
127.0.0.1:8092:80
```

`127.0.0.1` ограничивает доступ этим компьютером. `8092` — порт, куда отправляет запрос браузер или curl. `80` — порт веб-сервера внутри контейнера. Запрос `http://localhost:8092` Docker перенаправляет на порт 80 контейнера. [Описание ports](https://docs.docker.com/reference/compose-file/services/#ports).

В примере порт компьютера подставляется в строку:

```yaml
ports:
  - "127.0.0.1:${DEMO_PORT:-8092}:80"
```

При `DEMO_PORT=8093` строка станет `127.0.0.1:8093:80`. Если переменная отсутствует или пуста — `127.0.0.1:8092:80`. В задании подставляется **BANK_HTTP_PORT**, по умолчанию **8085**, а порт контейнера фиксирован: **8080**.

Значение `0` означает, что Docker выбирает свободный порт компьютера. В примере при `DEMO_PORT=0` фактический адрес узнаёшь так:

```shell
docker compose port preview 80
```

Например, вывод `127.0.0.1:32781` означает, что запрос надо отправить на `http://localhost:32781`. Порт внутри контейнера по-прежнему 80. Для твоего сервиса команда будет `docker compose port api 8080`. Тесты используют это, чтобы не зависеть от занятости порта 8085; специальную обработку числа 0 в Java писать не нужно.

### 5. environment и два вида значения по умолчанию

В этой строке слева — имя переменной **в контейнере**, справа — выражение, которое Compose вычислит **перед запуском**:

```yaml
environment:
  DISPLAY_NAME: "${DEMO_NAME-Guest}"
```

Если в `.env` записано `DEMO_NAME=alex`, контейнер получит `DISPLAY_NAME=alex`. Имена могут отличаться; в задании и источник, и переменная контейнера называются **BANK_REGION**.

Сравни два выражения:

| Источник NAME | `${NAME-default}` | `${NAME:-default}` |
|---|---|---|
| Переменная отсутствует | `default` | `default` |
| Переменная задана пустой строкой | пустая строка | `default` |
| Переменная равна `alex` | `alex` | `alex` |

Для региона нужно сохранить пустое заданное значение, поэтому используй вариант **без двоеточия** и значение по умолчанию `Local`. Для порта в примере двоеточие подходит: пустая строка не задаёт номер порта. Это синтаксис **Compose**. В конфигурации Spring выражение `${BANK_REGION:Local}` имеет другой синтаксис: не переноси запись из YAML в application.properties механически.

Настройка `environment` относится к создаваемому контейнеру. Она не изменяет JAR и Docker-образ. После редактирования `.env` контейнер нужно пересоздать, чтобы Java-процесс получил новое окружение.

### 6. .env, --env-file и env_file

Различай два действия: дать значения самому Compose для подстановки и передать переменные контейнеру.

| Запись | Где находится | Назначение |
|---|---|---|
| `.env` | отдельный файл рядом с compose.yaml | источник значений для подстановки Compose |
| `--env-file settings.env` | аргумент команды Docker Compose | выбирает другой источник вместо стандартного `.env` |
| `environment` | блок сервиса в compose.yaml | явно задаёт переменные контейнера |
| `env_file: settings.env` | поле сервиса в compose.yaml | загружает переменные из файла в окружение контейнера |

Для примера файл `settings.env` может содержать `DEMO_NAME=alex` и `DEMO_PORT=8093`. Тогда команда:

```shell
docker compose --env-file settings.env config
```

покажет `DISPLAY_NAME: alex` и публикацию порта 8093. После проверки запускай с тем же аргументом:

```shell
docker compose --env-file settings.env up -d --build
```

В задании **не добавляй поле `env_file` в YAML**: значение передаётся через явное выражение в `environment`. Тесты смогут подставить свой файл командой `--env-file`, не создавая и не изменяя твой `.env`. [Окружение контейнера](https://docs.docker.com/compose/how-tos/environment-variables/set-environment-variables/).

### 7. Работа из образа без volumes

`COPY` при сборке записывает файл в образ. Монтирование через `volumes` подключает файл или папку компьютера к работающему контейнеру. В этой практике используй первый способ: Java runtime и JAR находятся в образе, настройки передаются через окружение. Поле `volumes` не добавляй.

Проверяй два пути отдельно:

```text
Сборка: Maven → target/bank-service.jar → Dockerfile COPY → образ.
Запуск: .env → Compose environment → окружение контейнера → Spring → DTO.
Запрос: curl → порт компьютера → порт 8080 контейнера → контроллер → JSON.
```

Сначала добейся, чтобы `docker compose config` показывал ожидаемую сборку, порт и регион. Затем запусти контейнер и проверь JSON через curl. Требования задания и автоматические тесты остались прежними.

## Контракт API

`GET /bank/status` доступен без аутентификации. Порт приложения внутри контейнера — **8080**.

Ответ `200`, `Content-Type: application/json`, ровно два поля:

```json
{"service":"Transfer API","region":"Local"}
```

| Поле | Правило |
|---|---|
| `service` | всегда `Transfer API` |
| `region` | значение `BANK_REGION` при запуске; если настройка отсутствует — `Local` |

Сохраняй заданное значение точно: регистр, Unicode, кавычки и пробелы. Пустая заданная строка остаётся пустой строкой. Значение не вшивается в JAR или образ.

`GET /missing` возвращает `404`; `POST /bank/status` — `405`. Тела ошибок не фиксируются.

База, аутентификация и отдельный сервисный слой здесь не требуются. Каждый самостоятельный класс — отдельный файл. Обязательны пакет `learning.task091` и внешний HTTP-контракт; имена Java-классов свободные.

## Контракт файлов и Compose

Самостоятельно создай в корне **Dockerfile**, **.dockerignore** и **compose.yaml**. Настройки приложения размещай в `src/main/resources/`, код — в `src/main/java/learning/task091/`. Maven должен создавать исполняемый `target/bank-service.jar` на фазе `package` с байткодом Java 21. Подключай только необходимые зависимости.

Сохраняются ограничения №90: один этап Dockerfile, Java runtime 21, копирование готового JAR с хоста, `ENTRYPOINT` в JSON-форме с Java и `-jar`. Образ работает без монтирования файлов приложения с компьютера. `.dockerignore` содержит отдельные строки `.git`, `.idea`, `.maven-home`, `src`, `tasks` и `.env`; JAR не исключается.

В `compose.yaml`:

1. Ровно один сервис, обязательное имя **api**: оно используется в командах проверки.
2. Сервис собирается через `build` с контекстом текущего каталога проекта и файлом `Dockerfile`. Не задавай `image`: в этой практике имя образа назначает Compose по имени проекта и сервиса.
3. Не задавай `container_name`: имя проекта должно позволять независимые запуски одной конфигурации.
4. Ровно один TCP-порт: адрес компьютера **127.0.0.1**, порт приложения **8080**, порт компьютера — из **BANK_HTTP_PORT**, по умолчанию **8085**. Для тестов значение `0` должно позволять Docker выбрать свободный порт.
5. Через `environment` передай контейнеру **BANK_REGION**, подставив значение из окружения Compose. При отсутствии — **Local**, при пустой строке — пустая строка.
6. Используй подстановку в `environment`, без `env_file` сервиса. `--env-file` в команде выбирает файл для подстановки; это другой механизм, чем `env_file` внутри YAML.
7. Без volumes, других сервисов или файлов приложения с хоста. Сборка и запуск должны работать с Dockerfile, .dockerignore, compose.yaml, готовым JAR и внешним файлом настроек.

Настройки порта и региона меняются без правки YAML и без пересборки образа. При пересоздании контейнера API возвращает новое значение. Обычный `down` удаляет контейнеры проекта, сохраняя образ для следующего `up`.

## Ручная проверка: три примера

Сначала собери JAR:

```shell
JAVA_HOME=/home/kriksson/.jdks/temurin-21.0.12.1 PATH=/home/kriksson/.jdks/temurin-21.0.12.1/bin:$PATH MAVEN_USER_HOME="$PWD/.maven-home" bash ./mvnw -Dmaven.repo.local="$PWD/.maven-home/repository" -Dmaven.test.skip=true clean package
```

**1. Значения по умолчанию.** Без `BANK_REGION` и `BANK_HTTP_PORT` в окружении или `.env`:

```shell
docker compose up -d --build
curl -i http://localhost:8085/bank/status
```

Получишь `{"service":"Transfer API","region":"Local"}`.

**2. Другой регион и порт.** Создай локальный `.env` с `BANK_REGION=North` и `BANK_HTTP_PORT=8086`, затем:

```shell
docker compose config
docker compose up -d --no-build --force-recreate
curl -i http://localhost:8086/bank/status
```

Получишь `{"service":"Transfer API","region":"North"}` из того же образа.

**3. Пустая строка и сохранённый образ.** В `.env` запиши `BANK_REGION=`; порт оставь 8086:

```shell
docker compose down
docker compose up -d --no-build
curl -i http://localhost:8086/bank/status
```

Поле `region` будет `""`. Новый контейнер создаётся из сохранённого образа.

Для значения с пробелами и кавычками используй одинарные кавычки в файле, например `BANK_REGION='  Восток "офис" — №3  '`. Они оформляют значение и не попадают в ответ.

Посмотреть состояние и логи:

```shell
docker compose ps
docker compose logs api
docker compose down
```

`up` создаёт и запускает контейнер; `-d` оставляет его работать в фоне. `--build` сначала собирает образ. `--no-build` запрещает сборку, `--force-recreate` пересоздаёт контейнер с текущими настройками. Изменение `.env` не меняет окружение уже работающего процесса само по себе. `down` удаляет контейнеры и сеть проекта; образ по умолчанию сохраняется. [Команда up](https://docs.docker.com/reference/cli/docker/compose/up/), [команда down](https://docs.docker.com/reference/cli/docker/compose/down/).

`.env` оставь локальным: в репозитории он должен быть исключён через `.gitignore`. Сам проверь итоговые настройки через `config`, затем HTTP-ответ, ошибки и смену региона через `curl`. Проверки входящего JSON в Java здесь не нужны: запрос не имеет тела.
