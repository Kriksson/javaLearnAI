# Задача №80 — Хранители гильдии по страницам

**Сложность: базовая. Новый шаг после фильтрации и изменения JPA-связей.**

В большой гильдии список хранителей не помещается на одном экране. API должен возвращать небольшую страницу списка и сообщать, сколько всего хранителей подходит под фильтр. Самостоятельно спроектируй и собери приложение с нуля в пакете `learning.task080`. Имена Java-классов, полей и методов выбираешь сам.

Закрепляем: две JPA-сущности, `@ManyToOne`, внешний ключ, производный метод Spring Data, фильтр по гильдии и минимальному уровню, сортировку по двум полям, параметры URL, проверку существования гильдии и DTO.

Новые понятия: **`Pageable` / `PageRequest`** — описание запрашиваемой страницы; **`Page`** — результат с содержимым страницы и общими количествами. Новых зависимостей сверх знакомого Spring Boot / JPA не требуется.

## Как работает страница

Сначала база отбирает строки по фильтру и сортирует их, затем возвращает нужный участок результата. Нумерация страниц начинается с **нуля**. Для `page=1&size=2` нужно пропустить первые две подходящие строки и вернуть следующие две. Это вторая страница.

`PageRequest.of(page, size)` создаёт объект, реализующий интерфейс `Pageable`. Передай его дополнительным параметром производному методу репозитория. Spring Data использует его как инструкцию для ограничения выборки; это не ещё одно условие вроде имени или уровня. Возвращаемый тип такого метода — `Page<ТвояСущность>`.

`Page` содержит не только найденные объекты:

| Метод | Что означает |
|---|---|
| `getContent()` | Объекты только текущей страницы |
| `getNumber()` | Запрошенный номер страницы, начиная с 0 |
| `getSize()` | Запрошенный размер страницы |
| `getTotalElements()` | Число всех строк, подходящих под тот же фильтр; тип `long` |
| `getTotalPages()` | Число страниц с таким размером |

Если всего подходят 5 строк и размер страницы равен 2, страниц будет 3. На последней странице находится одна строка, но `getSize()` всё равно равен 2. При отсутствии совпадений общее число страниц равно 0. Запрос страницы за пределами списка возвращает пустое содержимое, сохраняя общий счётчик совпадений.

Для получения общего количества Spring Data при необходимости выполняет дополнительный запрос подсчёта. Не вычисляй `totalElements` через размер текущего списка.

[Документация Spring Data: параметры Pageable и результат Page](https://docs.spring.io/spring-data/commons/reference/3.5/repositories/query-methods-details.html#repositories.special-parameters).

### Отдельный работающий пример: страницы длинных книг

Пример компилируется в Spring Boot JPA приложении, где пакет `example.books` сканируется. Он остаётся в материале задания, среди файлов решения его размещать не нужно.

`Book.java`:

```java
package example.books;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

@Entity
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private int pages;

    protected Book() {}

    public Book(int pages) {
        this.pages = pages;
    }

    public Long getId() {
        return id;
    }
}
```

`@Entity` задаёт сущность; `@Id` и `IDENTITY` задают ID, получаемый от БД. Поле `pages` хранит длину книги; пустой конструктор нужен Hibernate.

`BookRepository.java`:

```java
package example.books;

import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jpa.repository.JpaRepository;

public interface BookRepository extends JpaRepository<Book, Long> {
    Page<Book> findByPagesGreaterThanEqualOrderByIdAsc(
            int minimumPages, Pageable pageable);
}
```

Имя метода задаёт фильтр по Java-полю `pages` и порядок по Java-полю `id`. `minimumPages` — значение порога; `pageable` — отдельная инструкция выбора страницы. `Page<Book>` позволяет получить и книги, и общие количества.

`BookCatalog.java`:

```java
package example.books;

import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.stereotype.Service;

@Service
public class BookCatalog {
    private final BookRepository repository;

    public BookCatalog(BookRepository repository) {
        this.repository = repository;
    }

    public Page<Book> read(int minimumPages, int page, int size) {
        if (minimumPages < 0 || page < 0 || size < 1) {
            throw new IllegalArgumentException("Invalid page request");
        }
        var request = PageRequest.of(page, size);
        return repository.findByPagesGreaterThanEqualOrderByIdAsc(
                minimumPages, request);
    }
}
```

- `@Service` регистрирует компонент, а конструктор получает репозиторий от Spring.
- Проверка защищает метод от отрицательного порога, отрицательной страницы и неположительного размера.
- `PageRequest.of` создаёт описание страницы; репозиторий ограничивает выборку в БД.
- Возвращаемый `Page` позволяет отдельно прочитать `getContent()` и общие количества.

Пусть в БД есть книги `(id, pages)`: `(1, 100)`, `(2, 220)`, `(3, 300)`, `(4, 240)`. Вызов внедрённого `catalog.read(200, 0, 2)` вернёт книги с ID `2` и `3`, `totalElements=3`, `totalPages=2`. Вызов `catalog.read(200, 1, 2)` вернёт только книгу `4`, но размер страницы останется 2, а общие количества — 3 и 2.

Полный путь данных в HTTP API: строки параметров URL → Spring MVC преобразует их в Java-числа → твой код проверяет диапазоны и существование родителя → создаёт `PageRequest` → передаёт значения фильтра и страницу репозиторию → Spring Data строит выборку с ограничением и при необходимости подсчёт → Hibernate создаёт сущности → код превращает содержимое в DTO и берёт метаданные из `Page` → Jackson сериализует ответ в JSON. Непреобразуемое число отклоняет Spring; проверки бизнес-диапазонов и существования гильдии пишешь ты.

## Модель и настройка

Используй H2 в памяти. Вручную создай `src/main/resources/application.properties`: URL начинается с `jdbc:h2:mem:`, пользователь `sa`, пустой пароль, `spring.jpa.hibernate.ddl-auto=create-drop`. Hibernate создаёт пустые таблицы. Начальные данные, `schema.sql` и `data.sql` не добавляй.

Создай две отдельные сущности. Явно отобрази таблицы через `@Table`, колонки через `@Column`, связь хранитель → гильдия через `@ManyToOne` и `@JoinColumn(name = "guild_id", nullable = false)`. Обратную коллекцию `@OneToMany` в этой задаче не добавляй.

| Таблица | Колонки |
|---|---|
| `guilds` | `id BIGINT` — identity primary key; `name VARCHAR(40) NOT NULL` |
| `guild_keepers` | `id BIGINT` — identity primary key; `name VARCHAR(40) NOT NULL`; `level INTEGER NOT NULL`; `guild_id BIGINT NOT NULL` — внешний ключ на `guilds.id` |

Используй Spring Data JPA репозитории для обеих сущностей; `JpaRepository` подходит. Производный метод репозитория хранителей должен возвращать `Page` сущностей и принимать значения фильтра и дополнительный параметр `Pageable`. Имя метода задаёт два условия через `And`: равенство ID связанной гильдии и уровень `GreaterThanEqual`. В имени также задай порядок: уровень по убыванию, затем ID хранителя по возрастанию. Конкретное имя зависит от выбранных тобой Java-полей.

## HTTP-контракт

```http
GET /guilds/{guildId}/keepers?minLevel=5&page=0&size=2
```

- `guildId` — ID гильдии типа `long`. Поддерживай ID больше `Integer.MAX_VALUE`.
- Все три параметра URL обязательны: `minLevel`, `page`, `size` — целые числа диапазона `int`.
- Допустимые значения: `minLevel >= 0`, `0 <= page <= 1000`, `1 <= size <= 5`.
- Ограничение размера не позволяет запрашивать весь список сразу; ограничение номера страницы не позволяет задавать произвольно большое смещение. Небольшой размер 5 выбран для наглядной практики; в реальном API предел зависит от сценария.
- Для существующей гильдии отбирай только её хранителей с `level >= minLevel`. Сначала сортируй по уровню DESC и ID ASC, затем выбирай страницу.
- Успех → `200 OK`, `Content-Type: application/json`. Корневой объект содержит ровно `content`, `page`, `size`, `totalElements`, `totalPages`.
- `content` — массив DTO, каждый содержит ровно `id`, `name`, `level`. JPA-сущности и объект `Page` напрямую в ответ не возвращай.
- `page` и `size` сохраняют запрошенные значения. `totalElements` — число всех совпадений в этой гильдии с этим порогом, тип `long`. `totalPages` — число страниц с этим размером.
- Существующая пустая гильдия или отсутствие совпадений → `200`, `content: []`, `totalElements: 0`, `totalPages: 0`.
- Страница за последней, но в допустимом диапазоне → `200`, пустой `content`; общие количества соответствуют всем совпадениям, даже если они ненулевые.
- При корректных параметрах неизвестная гильдия → `404`. Наличие хранителя с таким же собственным ID не означает наличие гильдии.
- Для существующей гильдии отсутствующий, пустой, состоящий из пробелов или непреобразуемый параметр, число вне диапазона `int` либо нарушение указанных границ → `400`. Формат тела ошибки свободный.
- Имена длиной 40 символов, кириллица и кавычки сохраняются. Допустимы уровни `0` и `Integer.MAX_VALUE`.
- Каждый запрос читает актуальное состояние БД: изменения уровня, имени и принадлежности хранителя отражаются и в содержимом, и в общих количествах.
- GET при любом исходе не изменяет ни одну строку. База отклоняет хранителя с отсутствующей или несуществующей гильдией.

## Примеры

Пусть гильдия `1` содержит хранителей `(id, name, level)`: `(10, "Mira", 5)`, `(20, "Rin", 7)`, `(30, "Low", 4)`, `(40, "Kai", 7)`, `(50, "High", 9)`, `(60, "Last", 5)`.

1. `GET /guilds/1/keepers?minLevel=5&page=0&size=2` → `200`:

```json
{
  "content": [
    {"id": 50, "name": "High", "level": 9},
    {"id": 20, "name": "Rin", "level": 7}
  ],
  "page": 0,
  "size": 2,
  "totalElements": 5,
  "totalPages": 3
}
```

2. Тот же запрос с `page=2` → `200`: в `content` только хранитель `60`, `page=2`, `size=2`, `totalElements=5`, `totalPages=3`. С `page=3` содержимое пустое, но общие количества остаются 5 и 3.
3. Для существующей гильдии `minLevel=10&page=0&size=2` → `200` с пустым содержимым и нулевыми общими количествами. `size=0` → `400`. Корректный запрос к несуществующей гильдии → `404`.

## Ограничения и критерии готовности

- Фильтрацию, сортировку и ограничение страницы выполняет БД через производный метод с `Pageable` и результатом `Page`. Создавай описание страницы через `PageRequest`.
- Не используй `@Query`, ручной SQL, `JdbcTemplate`, `findAll()`, фильтрацию/сортировку всех строк в Java или ручное разбиение через `skip`, `limit`, `subList`, `PageImpl`. Тесты используют JDBC только для независимой подготовки и проверки данных.
- Преобразование сущностей текущей страницы в DTO можно выполнять обычным циклом или Stream API. Общие количества бери из результата репозитория.
- Использование нужного метода и ограничения дополнительно проверяются при просмотре решения. Имена внутренних классов и методов тестам не важны.
- Готовность: верная схема и связь; стабильный порядок страниц; корректные общие количества; пустые страницы; `200`/`404`/`400`; большие ID и граничные уровни; актуальные данные без изменений от GET.
