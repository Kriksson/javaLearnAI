 # №90 — Банк: первый Docker-образ API

Сложность: **базовая**. Код приложения создаёшь в `learning.task090`; настройки Maven, Dockerfile и ресурсы тоже пишешь сам.

Закрепляем: Spring Boot REST, DTO, внешнюю конфигурацию, Maven, Java 21 и проверку HTTP-контракта.

Впервые: **исполняемый JAR** и **Docker-образ с запуском контейнера**. В этой практике JAR собираем на компьютере, затем кладём его в образ. Compose, PostgreSQL в контейнере и сборка в несколько этапов будут отдельными шагами.

## Сценарий

Банк открывает несколько отделений. Во всех работает одно небольшое информационное API, а название отделения задаётся при запуске. Нужно собрать приложение один раз и запускать одинаковый образ с разными значениями переменной окружения.

На этом шаге API публичное и не обращается к базе. Так проще разобраться в упаковке и запуске. Пользователей, роли, миграции и регистрацию реализовывать не требуется.

## Зачем нужен исполняемый JAR

До сих пор приложение запускала IntelliJ IDEA, которая подбирала классы и зависимости. Для запуска вне IDE нужен файл, с которым работает команда:

```shell
java -jar файл.jar
```

Обычный результат Maven `jar` может содержать только твои классы. Исполняемый Spring Boot JAR дополнительно содержит зависимости и загрузчик Boot. Его создаёт цель **repackage** плагина `org.springframework.boot:spring-boot-maven-plugin`. Внутри появляются `BOOT-INF/classes`, `BOOT-INF/lib` и записи manifest о загрузчике и стартовом классе.

В текущем учебном `pom.xml` нет Spring Boot parent. Поэтому сам добавь плагин версии `${spring.boot.version}` в `build/plugins` и выполнение его цели `repackage` на стадии `package`. Простого объявления плагина без выполнения цели недостаточно. Для имени выходного файла используй `build/finalName` со значением `bank-service`. Версия исходников остаётся **21**. [Упаковка исполняемого архива Spring Boot](https://docs.spring.io/spring-boot/3.5/maven-plugin/packaging.html).

## Образ и контейнер

**Образ** — подготовленный набор файлов для запуска: Java runtime, твой JAR и команда запуска. **Контейнер** — экземпляр, созданный из образа; он может работать или быть остановлен. Один образ можно использовать для нескольких контейнеров с разными настройками.

Dockerfile описывает сборку образа. Команда `build` читает Dockerfile и доступные файлы из **контекста сборки** — каталога, который ты передал последним аргументом. `.dockerignore` исключает лишние файлы из этого контекста. [Что такое образ](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/), [контекст сборки](https://docs.docker.com/build/concepts/context/#dockerignore-files).

### Отдельный работающий пример: консольное приветствие

Этот пример печатает приветствие и завершает процесс. Он не содержит банковского API и остаётся только в учебном материале. Создай его в отдельной временной папке.

`Banner.java`:

```java
package demo.banner;

public class Banner {
    public static void main(String[] args) {
        String displayName = System.getenv("DISPLAY_NAME");
        if (displayName == null) displayName = "Guest";
        System.out.println("Welcome, " + displayName);
    }
}
```

Собери и проверь исполняемый JAR обычного Java-приложения:

```shell
javac --release 21 -d classes Banner.java
jar --create --file banner.jar --main-class demo.banner.Banner -C classes .
java -jar banner.jar
# Welcome, Guest
```

`javac` создаёт байткод Java 21. `jar` собирает классы и записывает стартовый класс в manifest. `java -jar` находит этот класс и вызывает `main`. Здесь нет внешних библиотек; Spring Boot-приложению дополнительно нужна упаковка зависимостей через `repackage`.

Dockerfile **примера**:

```dockerfile
FROM docker.io/library/eclipse-temurin:21-jre
WORKDIR /tool
COPY banner.jar banner.jar
ENTRYPOINT ["java", "-jar", "banner.jar"]
```

- `FROM` задаёт исходный образ с Java runtime 21.
- `WORKDIR` задаёт рабочую папку внутри образа.
- `COPY` переносит собранный JAR из контекста сборки в образ.
- `ENTRYPOINT` задаёт команду при запуске контейнера. JSON-форма передаёт аргументы непосредственно процессу Java.

В этой отдельной папке:

```shell
docker build -t banner-demo:1 .
docker run --rm -e DISPLAY_NAME=alex banner-demo:1
# Welcome, alex
```

Точка означает, что контекст сборки — текущая папка. `banner-demo:1` — имя и тег образа. `run` создаёт и запускает контейнер, `-e` передаёт ему переменную, `--rm` удаляет контейнер после завершения.

Путь данных: `-e DISPLAY_NAME=alex` → переменная внутри контейнера → Java `main` → `System.getenv` → строка приветствия в логах. Переменная другого запуска не меняет собранный образ.

В банковском приложении используй уже знакомую конфигурацию Spring: значение `BANK_BRANCH` должно попадать в настройку отделения, а затем в DTO HTTP-ответа. Собственный разбор HTTP не нужен.

## Контракт приложения

`GET /bank/info` доступен без аутентификации. Порт приложения внутри контейнера — **8080**.

Ответ `200`, `Content-Type: application/json`, ровно два поля:

```json
{"name":"Practice Bank","branch":"Central"}
```

| Поле | Правило |
|---|---|
| `name` | всегда `Practice Bank` |
| `branch` | значение переменной окружения `BANK_BRANCH`; если переменная не задана — `Central` |

Переданное значение сохраняй точно: регистр, Unicode, кавычки и пробелы не меняются. Пустая заданная переменная даёт `"branch":""`; значение по умолчанию используется только при отсутствии переменной.

`GET /missing` возвращает `404`. `POST /bank/info` возвращает `405`, поскольку операция допускает только GET. Тела ошибок не фиксируются. Настройки отделения не должны записываться в JAR при сборке: один образ работает с разными значениями при запуске.

Сущности, репозитории и сервисный слой здесь не обязательны. Выбери минимальные роли компонентов самостоятельно. Каждый самостоятельный класс — отдельный файл; имя главного класса свободное, пакет — `learning.task090`.

## Контракт сборки и образа

1. `bash ./mvnw -Dmaven.test.skip=true package` создаёт **`target/bank-service.jar`**, запускаемый через `java -jar`. Упаковка выполняется автоматически на `package`. `maven.test.skip=true` здесь используется только для упаковки перед контейнерной проверкой; он не означает, что задача проверена.
2. В корне проекта находятся самостоятельно написанные **Dockerfile** и **.dockerignore**.
3. В Dockerfile **один этап** (`FROM`). Используй образ с Java runtime **21**; например, тот, который показан выше. Собранный JAR копируется из `target/bank-service.jar` в выбранный тобой путь внутри образа. Команда запуска — `ENTRYPOINT` в JSON-форме: Java, `-jar`, путь к JAR. В runtime-образе должна быть доступна команда `java -version`.
4. Сборка образа требует только Dockerfile, .dockerignore и готового JAR в `target/`. Maven, исходники и архив прошлых задач внутри образа не нужны. Не подключай файлы приложения с компьютера через bind mount: контейнер работает с JAR из образа.
5. В `.dockerignore` добавь отдельные строки `.git`, `.idea`, `.maven-home`, `src`, `tasks` и `.env`. Завершающий `/` у каталогов допустим. Файл `target/bank-service.jar` должен оставаться доступным для `COPY`; не исключай его.
6. Контейнер запускается одной командой `run`; значение `BANK_BRANCH` можно изменить без пересборки образа. Он не требует PostgreSQL, переменных `COURSE_PG_*` или HTTP Basic.

Проверь зависимости в `pom.xml`: для приложения достаточно Web, для проверки — JUnit 5 и Jackson (они уже доступны в текущем проекте). Старые зависимости Security, JPA, JDBC и Flyway в этой небольшой практике не нужны; убери их вместе с ненужными драйверами. Настройки сборки меняешь сам. Готовый Dockerfile приложения тренер не создаёт.

## Порты и ручная проверка

У контейнера собственный сетевой адрес. Чтобы обратиться к нему с компьютера, публикуем порт:

```shell
docker run --rm --name branch-api -p 127.0.0.1:8085:8080 -e BANK_BRANCH=Retail bank-api:90
```

`8085` — порт компьютера, `8080` — порт приложения внутри контейнера. Поэтому запрос отправляется на `http://localhost:8085/bank/info`. Запись `127.0.0.1` ограничивает публикацию этим компьютером. Инструкция `EXPOSE 8080` в Dockerfile может описывать порт, но сама по себе не заменяет `-p`. [Публикация портов Docker](https://docs.docker.com/get-started/docker-concepts/running-containers/publishing-ports/).

Полный путь запроса: `curl` → порт компьютера 8085 → опубликованный порт контейнера 8080 → Spring MVC → контроллер → настройка отделения из окружения → DTO → JSON.

Последовательность проверки:

```shell
# Сначала собери JAR через Maven package с JDK 21.
docker build -t bank-api:90 .
docker run --rm --name branch-api -p 127.0.0.1:8085:8080 -e BANK_BRANCH=Retail bank-api:90
```

В другом терминале:

```shell
curl -i http://localhost:8085/bank/info
docker logs branch-api
docker stop branch-api
```

### Три примера

1. Запуск без `-e BANK_BRANCH` → `{"name":"Practice Bank","branch":"Central"}`.
2. Запуск того же образа с `-e BANK_BRANCH=Retail` → `{"name":"Practice Bank","branch":"Retail"}`.
3. Два контейнера из одного образа с разными значениями отделения и разными портами компьютера возвращают каждый своё значение; образ не пересобирается.

## Инструменты и автоматические тесты

Для этой задачи используем **Docker Engine** и команду **docker**. Тесты обращаются только к Docker.

`docker` — клиент командной строки, `dockerd` — фоновая служба, которая управляет сборкой и контейнерами. Установленного CLI недостаточно: должен работать Docker daemon, а пользователь, запускающий тесты, должен иметь доступ к нему.

Если Docker Engine установлен, но служба не запущена, в своём терминале выполни:

```shell
sudo systemctl start docker
```

Затем проверь:

```shell
docker info
```

Если вместо сведений о сервере получишь `permission denied`, настрой доступ пользователя по [инструкции Docker для Linux](https://docs.docker.com/engine/install/linux-postinstall/). После изменения членства в группе нужно заново войти в систему и перезапустить IntelliJ, чтобы тесты получили новые права. Проверочная команда `sudo docker info` помогает отличить ошибку доступа от неработающей службы; Maven с sudo запускать не требуется.

Первый запуск образа может скачивать его из registry. [Запуск Docker Engine на Fedora](https://docs.docker.com/engine/install/fedora/#install-docker-engine).

Тесты тренера:

- `src/test/java/learning/task090/BankContainerApiTest.java` — **6 тестов**: исполняемый архив, Dockerfile и контекст, реальный запуск, внешний HTTP, конфигурация, границы и ошибки;
- `src/test/java/learning/task090/ContainerCommands.java` — инфраструктура запуска команд с таймаутами и логами.

Тесты сами выполняют отдельный `package` с отключённым запуском тестов, собирают временный образ и запускают контейнеры на свободных портах. Повторного запуска тестов из вложенной сборки нет. Контекст сборки временный: только Dockerfile, .dockerignore и готовый JAR. После сборки он удаляется; API должно продолжать работать из образа. Если контейнер завершился до готовности API, тест сразу показывает его логи; другие проверки того же варианта запуска используют эту ошибку без повторного ожидания. Для работающего контейнера предел ожидания API — 90 секунд. После проверки удаляются только созданные этими тестами контейнеры и временный образ; базовый образ остаётся в кеше. Логи команд находятся в `target/task090-checks/`.
