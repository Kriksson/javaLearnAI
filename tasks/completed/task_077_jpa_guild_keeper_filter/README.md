# Задача №77 — Поиск хранителей в гильдии

**Сложность:** небольшая проектная; дополнительная практика по просьбе ученика.

**Закрепи:** ручную сборку приложения, JPA-связь `@ManyToOne` / `@JoinColumn`, два разных ID, `JpaRepository`, производные методы, `@RequestParam`, DTO и JSON.

**Впервые в практике:** соединение нескольких условий производного запроса через `And`. Новые технологии не вводим.

## Сценарий

Командир ищет в выбранной гильдии хранителей с определёнными именем и уровнем. Хранители других гильдий и записи, совпадающие только по одному признаку, в результат не попадают.

Снова собери приложение с нуля в пакете `learning.task077`. Архив №76 можно читать как справочник, но текущие файлы и конфигурацию создаёшь сам. Каждый самостоятельный класс находится в отдельном файле; имена классов и Java-полей выбираешь ты.

## Сначала разберись в связи

Пример данных:

| `guilds.id` | `guilds.name` |
|---:|---|
| 3 | Silver Hawks |
| 7 | Red Wolves |

| `guild_keepers.id` | `name` | `level` | `guild_id` |
|---:|---|---:|---:|
| 4 | Mira | 3 | 3 |
| 12 | Mira | 5 | 3 |
| 8 | Mira | 3 | 7 |

У хранителя `4` собственный ID — `4`, а ID гильдии — `3`. Запрос к гильдии `3` с фильтрами `name=Mira` и `level=3` должен выбрать только хранителя `4`.

В таблице хранителей `guild_id` хранит ключ гильдии. В Java поле связи имеет тип сущности гильдии; `@ManyToOne` описывает принадлежность многих хранителей одной гильдии, а `@JoinColumn` задаёт колонку, в которой лежит ключ. При чтении Hibernate связывает строку хранителя с объектом гильдии.

`existsById` проверяет собственный ID сущности репозитория. Для решения, существует ли гильдия из URL, обращайся к репозиторию гильдий. Репозиторий хранителей используй для поиска её участников. Пустой список участников не доказывает отсутствие гильдии.

## Учебный пример: два условия через `And`

Это отдельный пример с игроками и возрастом, не готовое решение задания. Его код остаётся в материале.

`Player.java`:

```java
package demo;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

@Entity
public class Player {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;
    private int age;

    protected Player() {}
    public Player(String name, int age) {
        this.name = name;
        this.age = age;
    }
    public Long getId() { return id; }
    public String getName() { return name; }
    public int getAge() { return age; }
}
```

`PlayerRepository.java`:

```java
package demo;

import java.util.List;
import org.springframework.data.jpa.repository.JpaRepository;

public interface PlayerRepository extends JpaRepository<Player, Long> {
    List<Player> findByNameAndAgeOrderByIdAsc(String name, int age);
}
```

В отдельном Spring Boot приложении с этими сущностями и внедрённым репозиторием можно выполнить:

```java
repository.save(new Player("Mira", 25));
repository.save(new Player("Mira", 30));
repository.save(new Player("Kai", 25));
List<Player> result = repository.findByNameAndAgeOrderByIdAsc("Mira", 25);
```

Первая, вторая и третья строки сохраняют трёх игроков. Последняя возвращает только первого: имя и возраст должны совпасть одновременно.

Разбор имени метода:

| Часть | Значение |
|---|---|
| `findBy` | Начать условия поиска |
| `Name` | Сравнить Java-поле `name` с первым аргументом |
| `And` | Оба условия должны выполняться |
| `Age` | Сравнить Java-поле `age` со вторым аргументом |
| `OrderByIdAsc` | Упорядочить по собственному ID игрока по возрастанию |

Порядок аргументов соответствует порядку условий. Сортировка не требует дополнительного аргумента. Названия Java-полей должны существовать в сущности: Spring Data проверяет их при запуске и создаёт реализацию интерфейса репозитория. Обычный произвольно названный метод Java такой механизм не получает.

При обращении к HTTP API полный путь будет таким: URL `...?name=Mira&age=25` → `@RequestParam` читает имя как `String`, возраст преобразует в `int` → код проверяет допустимость значений → вызывает метод с аргументами `"Mira"`, `25` → Spring Data строит запрос с двумя условиями равенства → Hibernate загружает сущности → код формирует DTO → Jackson создаёт JSON ответа.

Для текущего задания добавляется уже знакомый путь к ID связанной гильдии. Самостоятельно составь название метода для трёх условий: гильдия, имя хранителя, уровень. Сначала выпиши условия словами и порядок аргументов на бумаге, затем переведи их в имя метода. Механизм описан в [документации Spring Data](https://docs.spring.io/spring-data/jpa/reference/3.5/jpa/query-methods.html).

## Что собрать

Самостоятельно создай стартовый класс Spring Boot, две JPA-сущности, репозитории, контроллер и DTO элемента ответа. Отдельный сервис не требуется для этого простого чтения. В сущности хранителя используй обязательную связь `@ManyToOne` с гильдией и `@JoinColumn`; обратную коллекцию `@OneToMany` пока не добавляй.

Используй существующее учебное Maven-окружение: Spring Web, Spring Data JPA и H2 уже подключены. Дополнительные зависимости не нужны. Исходный код остаётся Java 21.

Создай `src/main/resources/application.properties`: отдельная in-memory база H2, пользователь `sa`, пустой пароль, `spring.jpa.hibernate.ddl-auto=create-drop`. Hibernate создаёт схему, таблицы при запуске пусты. Начальные данные и `schema.sql` не нужны.

| Таблица | Колонки |
|---|---|
| `guilds` | `id BIGINT` — identity primary key; `name VARCHAR(40) NOT NULL` |
| `guild_keepers` | `id BIGINT` — identity primary key; `name VARCHAR(40) NOT NULL`; `level INTEGER NOT NULL`; `guild_id BIGINT NOT NULL` — внешний ключ на `guilds.id` |

Для выборки объяви и используй производный метод `JpaRepository` с тремя условиями равенства через `And` и сортировкой по ID хранителя по возрастанию. Имена Java-полей и соответствующее название метода выбираешь сам. Не используй `findAll()` с фильтрацией в Java, `@Query`, ручной SQL или `JdbcTemplate` в приложении. Тесты используют JDBC только для подготовки и независимой проверки данных.

## HTTP-контракт

```text
GET /guilds/{guildId}/keepers?name=Mira&level=3
```

- `guildId` — ID гильдии. Параметры `name` и `level` обязательны.
- Для существующей гильдии и корректных параметров верни `200 OK`, `Content-Type: application/json` и массив хранителей, у которых одновременно совпадают гильдия, имя и уровень.
- Имя сравнивается точно, с учётом регистра; перед поиском его не обрезай и не меняй регистр. Уровень сравнивается на равенство.
- Массив отсортирован по собственному `id` хранителя по возрастанию. Каждый элемент содержит ровно `id`, `name`, `level`; данные гильдии в него не включаются.
- Существующая гильдия без совпадений или без хранителей → `200` и `[]`.
- Неизвестная гильдия при корректных фильтрах → `404`; формат тела ошибки свободный.
- Для существующей гильдии некорректные фильтры → `400`: имя пустое, состоит только из пробелов или длиннее 40 символов; уровень отрицательный; параметр отсутствует; уровень не преобразуется в `int`. Формат тела ошибки свободный.
- Допустимы имя длиной 40 символов, кириллица и кавычки в имени, уровни `0` и `Integer.MAX_VALUE`, ID больше `Integer.MAX_VALUE`.
- GET не изменяет строки обеих таблиц, включая ответы `400` и `404`. Каждый новый запрос видит актуальные принадлежность, имя и уровень хранителя после изменений в БД.
- База отклоняет хранителя с отсутствующей или несуществующей гильдией.

Проверки, которые ты пишешь в приложении: обязательные параметры и их преобразование обрабатывает Spring MVC; допустимость имени и уровня проверяешь ты; существование гильдии проверяешь через её репозиторий; список результата преобразуешь в DTO с тремя указанными полями. Подходящие значения для условий передаёшь в репозиторий в том же порядке, в котором условия записаны в названии метода.

Примеры для таблиц в начале задания:

1. `/guilds/3/keepers?name=Mira&level=3` → `200` и `[{"id":4,"name":"Mira","level":3}]`.
2. `/guilds/3/keepers?name=Mira&level=9` → `200` и `[]`.
3. `/guilds/99/keepers?name=Mira&level=3` → `404`, если гильдии `99` нет.
