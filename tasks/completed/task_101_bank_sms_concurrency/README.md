# Задача №101 — Банк: три consumer отправляют SMS параллельно

**Сложность:** базовая интеграционная, следующий шаг после №100. **Статус:** решена и архивирована 24.10.2026. Подтверждённый прогресс — **101** задача. Все **33 теста** прошли с настоящим Kafka и локальным HTTP-шлюзом, без ошибок и пропусков.

**Закрепляем:** публикацию JSON с ключом клиента, подтверждение отправки, ConsumerRecord, реальные partition/offset, потокобезопасное хранение и валидацию API.

**Новое:** `concurrency` одного listener и наблюдаемая параллельная обработка; синхронный HTTP-вызов внутри обработки Kafka-записи. JDK HttpClient уже встречался в курсе, теперь используем его в обработчике события.

## 1. Какую проблему решаем

Рассматриваем **только SMS**, один topic и одну операцию обработки. Отправка SMS требует HTTP-запроса к шлюзу. Пока шлюз готовит ответ, выполняющий эту операцию поток ждёт.

Допустим, входящий поток — 30 запросов в секунду, а один последовательный consumer успевает обработать 10. Необработанные записи накапливаются. Это условные числа для объяснения ограничения, не результаты измерения Kafka.

Можно создать три consumer **одной группы**, выполняющие один и тот же метод обработки. Topic с тремя partitions позволяет разделить работу:

```text
Один topic bank.sms.v1, везде один тип — SMS:

partition 0 → consumer 1 → HTTP-запрос к шлюзу
partition 1 → consumer 2 → HTTP-запрос к шлюзу
partition 2 → consumer 3 → HTTP-запрос к шлюзу
```

Код listener пишется один раз. `concurrency=3` создаёт три consumer, а не три разных бизнес-операции. Каждый обрабатывает свои записи. Для реальной параллельной работы сообщения должны находиться в разных partitions; один постоянный key не распределит нагрузку между всеми тремя.

| Настройка | Значение | Зачем |
|---|---:|---|
| Partitions | 3 | Разделить поток и дать работу трём consumer одной группы |
| Listener concurrency | 3 | Создать три consumer для одного метода listener |
| Replication factor | 1 | В учебном окружении один брокер; это число копий данных, а не обработчиков |

В №100 один consumer группы мог читать все partitions последовательно. **Теперь проверяем реальный эффект:** три запроса к шлюзу должны начаться до получения ответа на любой из них. Тест удерживает ответы, чтобы последовательное выполнение не смогло случайно выдать себя за параллельное. Бенчмарк скорости и точный прирост запросов в секунду не требуются.

## 2. Где выполняется работа

```text
Входящий POST API → валидация → одна запись в Kafka → подтверждение → 202
                                      ↓
                         один из трёх consumer группы
                                      ↓
                       исходящий HTTP POST к SMS-шлюзу
                                      ↓
                           дождаться ответа шлюза
                                      ↓
                        сохранить обработанное уведомление

GET API → выбрать сохранённые уведомления клиента → JSON
```

Входящий POST обрабатывает Spring-контроллер. Исходящий HTTP POST приложение отправляет из пути обработки listener через `HttpClient`. Сам Kafka SMS не отправляет. Шлюз в этой задаче — локальный HTTP-сервер тестов; реальной отправки SMS нет.

После подтверждения Kafka клиент API получает `202`, даже если шлюз ещё не ответил. В GET уведомление появляется **после успешного ответа шлюза**. Поэтому запись в Kafka и успешная обработка — два разных результата.

Если шлюз задержал сообщение из partition 0, consumer этой partition ждёт. Consumer partitions 1 и 2 могут продолжать работу. Следующая запись **той же partition 0** должна ждать предыдущую: порядок обработки сохраняется.

Сначала изучи [EXAMPLE.md](EXAMPLE.md): это отдельный рабочий проект с посылкой, настоящим Kafka и HTTP-сервером. В нём можно увидеть три одновременных запроса без написания банковского API.

## 3. Контракт Kafka

| Параметр | Обязательное значение |
|---|---|
| Topic | `bank.sms.v1` |
| Partitions / replicas | `3` / `1` |
| Consumer group | `bank-sms-senders-v1` |
| Consumer в группе | `3`, через один `@KafkaListener` с `concurrency="3"` или эквивалентную настройку стандартного контейнера |
| Key | `clientId`, преобразованный в строку |
| Value | JSON-строка ровно с полями `clientId` и `text` |

Объяви topic через `NewTopic`/`TopicBuilder`, используй строковые serializer/deserializer, `auto-offset-reset=earliest` и producer `acks=all`. Адрес бери из `spring.kafka.bootstrap-servers`, в тестах он подставляется автоматически. Приложение публикует без ручного указания partition; стандартное распределение по key остаётся за producer.

Параллельное чтение организует Kafka listener container. Собственные потоки, `ExecutorService`, `parallelStream`, `sendAsync()` и запуск обработки «в фоне» внутри listener здесь не используются. Обработчик синхронно завершает работу с одной записью; параллелизм создают три consumer для разных partitions. Так сохраняется смысл завершения обработки и порядок внутри partition.

Тестовый producer может явно указывать partition для управляемого сценария. Это код проверки, а не требование к твоей публикации.

## 4. Контракт HTTP

### POST /api/sms-requests

```json
{"clientId":17,"text":"Карта готова"}
```

- `clientId` — обязательное число типа `long`, от 1 до `Long.MAX_VALUE`.
- `text` — обязательная непустая строка, не только пробельные символы, длина 1–120 по `String.length()`.
- Сохраняй текст без изменений, включая пробелы, кириллицу, кавычки и переводы строк.
- Корректный запрос создаёт одну запись Kafka и возвращает `202` с пустым телом после подтверждения публикации. Ожидание результата отправки ограниченное, как в №99–100. Ошибка публикации не должна превращаться в успешный ответ.
- Некорректные или отсутствующие поля, пустое/отсутствующее тело и сломанный JSON дают `400` без публикации. Формат тела ошибки свободный.
- Контроллер не вызывает SMS-шлюз и не записывает уведомление в список обработанных.

### Исходящий запрос к учебному SMS-шлюзу

Полный URL бери из свойства **`bank.sms-gateway-url`**. Тесты передают случайный локальный адрес вместе с путём, например `http://127.0.0.1:54321/gateway/sms`. Не дописывай к нему свой путь и не фиксируй порт в коде.

На каждую полученную запись listener выполняет один HTTP POST с `Content-Type: application/json` и телом:

```json
{"clientId":17,"text":"Карта готова"}
```

JSON содержит только эти два поля. В обычных сценариях тестовый шлюз отвечает `204 No Content`; в проверках параллелизма он сначала удерживает ответ. После получения успешного ответа добавь уведомление в потокобезопасное хранилище вместе с `partition` и `offset` из ConsumerRecord.

Используй синхронный `java.net.http.HttpClient.send(...)`. Это блокирует только выполняющий запрос consumer. Один готовый `HttpClient` можно переиспользовать, а `HttpRequest` и его builder создавай заново для каждой операции. Builder изменяемый, не храни один общий builder для трёх потоков. Настрой ограниченные ожидания подключения и ответа; в примере — 2 и 10 секунд соответственно.

Ретраи, DLT, дедупликация, политика обработки неуспешного ответа шлюза и восстановление списка после перезапуска будут отдельными шагами. В этой задаче шлюз возвращает успешный ответ после управляемой задержки.

### GET /api/sms-requests?clientId=17

```json
[
  {"clientId":17,"text":"Карта готова","partition":1,"offset":8}
]
```

`partition` и `offset` в примере условные; используй реальные значения Kafka.

- Ответ — `200` и список только успешно обработанных уведомлений данного клиента. Для неизвестного клиента — `[]`.
- Пока шлюз не ответил, его уведомления в списке нет.
- `clientId` обязателен; пустое значение, ноль, отрицательное число, буквы и переполнение `long` дают `400`.
- `clientId` в JSON ответа — число. Согласуй числовой тип ID в DTO, контроллере и поиске; строковым он становится только для Kafka key.
- GET не удаляет элементы и возвращает отдельный список результата. Записи одного клиента сохраняют порядок его partition; общего порядка всех partitions нет.

## 5. Потоки и состояние

Spring обычно вызывает один объект listener из трёх consumer-потоков. Локальные переменные конкретного вызова принадлежат этому вызову. Общее хранилище должно быть потокобезопасным: `ConcurrentLinkedQueue` из предыдущих задач подходит.

Не сохраняй «текущее сообщение» в изменяемом поле singleton-сервиса или listener. Пока один вызов ждёт шлюз, второй может заменить это поле. Используй локальные DTO и передавай значения аргументами. Общая блокировка вокруг HTTP-вызова тоже сведёт параллельную обработку к последовательной.

## 7. Критерии приёмки

| Требование | Проверка |
|---|---|
| Topic 3 × 1; три настоящих consumer одной группы, по partition каждому | `topicHasThreePartitionsAndThreeRealConsumerMembers` |
| Один POST создаёт одну запись; шлюз получает правильные JSON, метод и Content-Type | `postPublishesOneRecordAndGatewayReceivesTheOriginalJson` |
| Данные из каждой partition доходят до шлюза и GET | `everyPartitionForwardsAnIndependentProducerRecordToTheGateway` |
| Три HTTP-запроса начались до освобождения любого ответа | `threePartitionsReachTheGatewayBeforeAnyGatewayReplyIsReleased` |
| Задержанная partition не блокирует другую | `anotherPartitionProgressesWhileOneGatewayRequestIsBlocked` |
| Записи одной partition обрабатываются последовательно | `samePartitionKeepsProcessingOrderWhileAnotherPartitionWorks` |
| POST возвращает 202 до ответа шлюза; до завершения HTTP запись не видна в GET | `postAcknowledgesKafkaWithoutWaitingForTheGatewayReply` |
| Неизвестный клиент и границы текста/long | `unknownClientReturnsEmptyArray`, `textLengthBoundariesAreAccepted`, `positiveLongBoundariesAreAccepted` |
| Ошибки POST и GET дают 400 без лишней публикации | `invalidPostReturns400AndPublishesNothing`, `invalidClientQueryReturns400` |

На ревью проверяются стандартный listener concurrency, отсутствие самостоятельного фонового запуска, потокобезопасность и ограниченные ожидания. Все тесты и тестовую инфраструктуру готовит тренер. Самостоятельные тесты тебе не назначаются.
