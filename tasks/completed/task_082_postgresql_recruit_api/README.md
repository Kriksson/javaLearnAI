# Задача №82 — Рекруты в PostgreSQL

**Сложность: базовая. Первое Spring Boot JPA приложение с отдельным PostgreSQL.**

Теперь список рекрутов должен жить в отдельной базе и сохраняться после остановки Java-приложения. Самостоятельно собери приложение с нуля в пакете `learning.task082`. Чтобы сосредоточиться на подключении, API будет небольшим: создание рекрута и чтение по ID.

Закрепляем: JPA-сущность, identity ID, `JpaRepository.save` / `findById`, DTO, Bean Validation или ручные проверки, `201 Created` с `Location`, `200` / `404` / `400`, внешнюю конфигурацию.

Новые понятия: **подключение Spring Boot к PostgreSQL через JDBC-драйвер** и **сохранение схемы и данных между запусками**. Docker, Flyway и Testcontainers пока не требуются; их введём отдельно.

## Что меняется после H2

PostgreSQL работает отдельным процессом. Приложение подключается к нему по адресу, порту и имени базы. Hibernate по-прежнему превращает строки в сущности, а методы репозитория работают с Java-объектами. Внешняя цепочка теперь такая:

```text
HTTP → контроллер → сервис/репозиторий → Hibernate → JDBC-драйвер → PostgreSQL
```

Нужен драйвер `org.postgresql:postgresql` с областью `runtime`. В этом окружении доступна версия `42.7.13`; если зависимости не управляются Spring Boot BOM, укажи её явно. Подключение H2 для этой задачи убери из `pom.xml`. Остальные необходимые зависимости и сборку проверяешь самостоятельно. Исходный код остаётся Java 21.

JDBC URL вида `jdbc:postgresql://localhost:5432/library` означает: сервер на `localhost`, порт `5432`, база `library`. Java-пользователь и пароль подключения — это учётные данные PostgreSQL, а не логин Linux. База и пользователь должны существовать до запуска приложения; Hibernate создаёт таблицы внутри базы, но не создаёт саму базу или пользователя.

[Драйвер и JDBC URL PostgreSQL](https://jdbc.postgresql.org/documentation/use/).

### Отдельный работающий пример: проверить подключение к библиотеке

Пример запускается с PostgreSQL-драйвером в classpath и переменными `LIBRARY_PG_URL`, `LIBRARY_PG_USER`, `LIBRARY_PG_PASSWORD`. Это самостоятельный учебный пример, среди файлов решения его не размещай.

```java
package example.library;

import java.sql.DriverManager;

public class LibraryConnectionCheck {
    public static void main(String[] args) throws Exception {
        String url = System.getenv("LIBRARY_PG_URL");
        String user = System.getenv("LIBRARY_PG_USER");
        String password = System.getenv("LIBRARY_PG_PASSWORD");

        try (var connection = DriverManager.getConnection(url, user, password)) {
            System.out.println(connection.getMetaData().getDatabaseProductName());
        }
    }
}
```

- `System.getenv` получает параметры из окружения процесса; значения заранее задаёт запускающий приложение человек.
- `DriverManager.getConnection` обращается к отдельному серверу. JDBC-драйвер должен быть доступен во время запуска.
- `getDatabaseProductName()` возвращает `PostgreSQL`, если подключение действительно ведёт к нему.
- `try` с ресурсом закрывает соединение после работы.

В Spring Boot соединения создаёт `DataSource`: параметры берутся из `spring.datasource.*`. Для подстановки переменной окружения используется запись `${ИМЯ_ПЕРЕМЕННОЙ}`. Например, в отдельном приложении библиотеки:

```properties
spring.datasource.url=${LIBRARY_PG_URL}
spring.datasource.username=${LIBRARY_PG_USER}
spring.datasource.password=${LIBRARY_PG_PASSWORD}
```

Полный путь: переменная окружения с JDBC URL → Spring подставляет её значение в свойство → создаёт `DataSource` → Hibernate использует соединение PostgreSQL → запрос репозитория читает или записывает строку. Неверный адрес, отсутствующая база, неверный пароль или отсутствующий драйвер мешают приложению подключиться; проверки тела HTTP-запроса пишешь ты отдельно.

## Почему здесь не create-drop

`create-drop` удаляет созданную Hibernate схему при закрытии контекста. Для сохранения данных в этой учебной практике используй **`spring.jpa.hibernate.ddl-auto=update`**: Hibernate создаёт отсутствующие таблицы или обновляет схему при запуске и не удаляет её при остановке.

Например, для отдельного JPA-приложения библиотеки с уже созданной сущностью `Book`:

```properties
spring.jpa.hibernate.ddl-auto=update
```

Первый запуск с пустой базой создаёт таблицу книг. Сохранённая через репозиторий книга остаётся в PostgreSQL после остановки приложения. При следующем запуске `findById` загружает прежнюю запись. В будущей практике управление схемой перенесём в миграции Flyway; сейчас проверяем подключение и сохранность данных.

[Инициализация схемы Hibernate](https://docs.spring.io/spring-boot/3.5/how-to/data-initialization.html#howto.data-initialization.using-hibernate), [подстановка внешних свойств](https://docs.spring.io/spring-boot/3.5/reference/features/external-config.html#features.external-config.files.property-placeholders).

## База и конфигурация приложения

Подними PostgreSQL обычным установленным сервером или используй свой уже работающий сервер. В этом Linux-окружении установлен PostgreSQL 18. Создай **отдельную учебную базу** и пользователя-владельца. Пользователю нужно право создавать таблицы и схемы в этой базе. Способ создания базы выбираешь сам: `psql`, IntelliJ Database или другой клиент.

Вручную создай `src/main/resources/application.properties` с такими требованиями:

| Свойство | Значение |
|---|---|
| `spring.datasource.url` | Подстановка `${COURSE_PG_URL}` без значения по умолчанию |
| `spring.datasource.username` | Подстановка `${COURSE_PG_USER}` |
| `spring.datasource.password` | Подстановка `${COURSE_PG_PASSWORD}` |
| `spring.jpa.hibernate.ddl-auto` | `update` |
| `spring.jpa.open-in-view` | `false` |

Перед запуском задавай эти три переменные окружения и для приложения, и для тестов. JDBC URL начинается с `jdbc:postgresql://` и не содержит параметра `currentSchema`: тесты добавляют его сами. Пароль не записывай в Git. В IntelliJ переменные задаются в Environment variables конфигурации запуска; переменные терминала автоматически не становятся настройками отдельной конфигурации IDEA.

Не добавляй `schema.sql`, `data.sql`, начальные данные, фиксированный `schema` в `@Table` или код, который очищает таблицы при запуске/остановке. По условию таблицу создаёт Hibernate, а данные должны сохраняться.

## Модель

Создай одну JPA-сущность с явными `@Table` и `@Column`:

| Таблица | Колонки |
|---|---|
| `recruits` | `id BIGINT` — identity primary key; `name VARCHAR(40) NOT NULL`; `level INTEGER NOT NULL` |

ID выдаёт PostgreSQL через `GenerationType.IDENTITY`. Новому рекруту приложение не назначает ID самостоятельно. Используй Spring Data JPA репозиторий; `JpaRepository` подходит. Имена Java-классов, полей и внутренних методов выбираешь сам.

## HTTP-контракт

### Создание

```http
POST /recruits
Content-Type: application/json

{"name":"Mira","level":3}
```

- Входной DTO содержит `name` и `level`. Имя обязательно, не пустое и не состоящее только из пробелов, длина не больше 40 символов. Уровень обязателен, не `null`, допустим от 0 до `Integer.MAX_VALUE`.
- Корректный запрос → `201 Created`, заголовок `Location: /recruits/{выданныйId}`, JSON с ровно тремя полями: `id`, `name`, `level`. ID положительный и соответствует фактической новой строке в PostgreSQL.
- Допустимы имя длиной 40 символов, кириллица, кавычки и пробелы вокруг непустого имени. Сохраняй имя без обрезания и преобразования.
- Повтор одинакового POST создаёт ещё одного рекрута с другим ID. Уникальность имени здесь не требуется; прежние строки не меняются.
- Отсутствующее тело, JSON `null`, отсутствующие или `null` поля, пустое/пробельное/слишком длинное имя, отрицательный уровень, повреждённый JSON, непреобразуемый уровень или число вне диапазона `int` → `400` без изменения существующих строк и без новой записи. Формат ошибки свободный.

Spring/Jackson создаёт DTO из JSON. Обязательность, длину и диапазон проверяешь ты — через Bean Validation или вручную. Для отсутствующего уровня входной DTO должен отличать отсутствие значения от нуля. Затем сохраняешь новую сущность через репозиторий и используешь выданный базой ID в DTO и `Location`.

### Чтение

```http
GET /recruits/{id}
```

- ID имеет диапазон `long`; поддерживай значения больше `Integer.MAX_VALUE`.
- Существующая запись → `200`, `Content-Type: application/json`, DTO с ровно `id`, `name`, `level`.
- Неизвестный или удалённый ID → `404`.
- Читай актуальные данные PostgreSQL: изменения имени и уровня, выполненные клиентом БД после предыдущего запроса, отражаются в следующем ответе.
- GET не изменяет строки. JPA-сущность напрямую в JSON не возвращай.
- База отклоняет `NULL` для имени и уровня.

### Сохранность

Созданный рекрут доступен после закрытия и повторного открытия Spring Boot JPA контекста с тем же подключением. Не удаляй таблицы, не очищай данные и не заменяй PostgreSQL локальной коллекцией или H2. После обычной остановки и запуска своего приложения проверь GET по ранее полученному ID.

## Примеры

1. POST `{"name":"Mira","level":3}` → `201`, например `Location: /recruits/12` и `{"id":12,"name":"Mira","level":3}`. ID `12` только иллюстрация: настоящий ID получает база.
2. Перезапусти приложение с той же базой. GET `/recruits/12` → `200` с прежней записью. Если в БД изменить уровень на 7, следующий GET вернёт 7.
3. POST `{"name":"   ","level":3}` → `400`; GET по отсутствующему ID → `404`. Ни один из этих запросов не меняет существующих рекрутов.

## Файлы, тесты и ограничения

- Вручную создавай рабочие Java-файлы в `src/main/java/learning/task082/`: стартовый класс, сущность, репозиторий, контроллер, DTO запроса и ответа. Сервис добавляй, если он помогает организовать код. Каждый самостоятельный класс — отдельный файл.
- Конфигурацию, PostgreSQL-драйвер в `pom.xml` и окружение запуска настраиваешь сам. Изменять `maven.compiler.release=21` не нужно.
- Тесты тренера: `src/test/java/learning/task082/PostgresRecruitApiTest.java`; инфраструктура тестов: `src/test/java/learning/task082/PostgresTestDatabase.java`.
- Тесты используют **настоящий PostgreSQL**, создают отдельную схему `task082_<случайныйИдентификатор>`, направляют приложение в неё и удаляют только эту схему после проверки. Таблицу `recruits` в этой схеме должен создать Hibernate твоего приложения. Таблицы обычного запуска приложения не используются тестами.
- Тесты не подменяют `ddl-auto`: проверяется твоя конфигурация `update`, в том числе при повторном открытии контекстов. Параметры подключения тесты направляют в свою схему; содержание application.properties проверяется отдельно.
- Не используй ручной SQL, `JdbcTemplate`, `@Query` или локальную коллекцию в приложении. Тесты используют JDBC для независимой подготовки и проверки базы. Ограничения и использование DTO дополнительно проверяются при просмотре решения.
- Готовность: PostgreSQL вместо H2, внешнее подключение, правильная identity-схема, JPA-запись и чтение, DTO, валидация, `201` / `200` / `404` / `400`, актуальные данные и сохранение после повторного открытия контекста.
