# Задача №78 — Хранители для сложного рейда

**Сложность: базовая. Дополнительная практика связей JPA и производных методов.**

Перед рейдом нужно получить хранителей одной гильдии, достигших заданного уровня. Самостоятельно спроектируй и собери приложение с нуля в пакете `learning.task078`. Имена Java-классов, полей и методов выбираешь сам. Тренер предоставляет условие и тесты; исходные файлы и конфигурацию создаёшь ты.

Закрепляем: две сущности, `@ManyToOne`, `@JoinColumn`, путь к ID связанной сущности в производном методе, `And`, проверку гильдии через её репозиторий, параметры URL и список DTO.

Два небольших новых приёма: `GreaterThanEqual` для условия «больше или равно» и порядок по двум полям в `OrderBy`. Другие технологии не вводятся.

## Как читать название метода

Репозиторий выбирается по типу объектов, которые нужно получить. Когда нужны хранители, запрос объявляется в репозитории хранителей. Условие принадлежности проходит по Java-связи хранитель → гильдия → её ID. Название производного метода содержит имена **Java-полей**, а аннотации переводят их в имена SQL-таблиц и колонок.

`GreaterThanEqual` после имени числового поля обозначает `>=`. Порог включается в результат: при минимуме `5` подходят уровни `5`, `6`, `9`, но не `4`.

В `OrderBy` можно последовательно указать два поля. Первое определяет основной порядок, второе разрешает совпадения. Например, уровни `9, 5, 5` идут по убыванию; два хранителя уровня `5` располагаются по возрастанию своего ID. Это делает ответ предсказуемым при повторных запросах.

### Отдельный пример: книги по числу страниц

Этот пример показывает новые приёмы на другом случае. Он компилируется в Spring Data JPA приложении, где пакет `example.books` сканируется для сущностей и репозиториев. Код остаётся учебным материалом; в файлы решения его не копируй.

`Book.java`:

```java
package example.books;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

@Entity
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private int pages;

    protected Book() {}

    public Book(int pages) {
        this.pages = pages;
    }

    public Long getId() { return id; }
    public int getPages() { return pages; }
}
```

`@Entity` делает книгу JPA-сущностью; `@Id` задаёт идентификатор; `IDENTITY` получает его от базы. Поле `pages` хранит число страниц. Пустой конструктор нужен Hibernate, второй позволяет создать книгу в Java.

`BookRepository.java`:

```java
package example.books;

import java.util.List;
import org.springframework.data.jpa.repository.JpaRepository;

public interface BookRepository extends JpaRepository<Book, Long> {
    List<Book> findByPagesGreaterThanEqualOrderByPagesDescIdAsc(int minimumPages);
}
```

- `JpaRepository<Book, Long>` задаёт тип результата и ID.
- `PagesGreaterThanEqual` сравнивает Java-поле `pages` с переданным аргументом через `>=`.
- `OrderByPagesDescIdAsc` сортирует сначала по страницам по убыванию, затем по ID по возрастанию.
- Spring создаёт реализацию интерфейса; тело этого метода писать не нужно.

Если в таблице книги `(id=4, pages=200)`, `(id=2, pages=200)` и `(id=8, pages=350)`, вызов `repository.findByPagesGreaterThanEqualOrderByPagesDescIdAsc(200)` возвращает книги с ID `8, 2, 4`. Книга со 199 страницами в результат не попадёт.

Полный путь данных в таком API: URL `?minPages=200` → Spring MVC преобразует строку `"200"` в `int` аргумента `@RequestParam("minPages")` → код проверяет неотрицательность → передаёт число в репозиторий → Spring Data строит запрос с `pages >= 200` и указанным порядком → Hibernate создаёт объекты `Book` из строк результата → контроллер преобразует их в DTO → клиент получает JSON. При отсутствии обязательного параметра или невозможном преобразовании Spring MVC возвращает `400` до вызова метода контроллера. Проверку отрицательного числа пишет разработчик.

[Ключевые слова и сортировка Spring Data](https://docs.spring.io/spring-data/jpa/reference/3.5/repositories/query-keywords-reference.html).

## Модель и ограничения

Приложение работает с H2 в памяти. Вручную создай `src/main/resources/application.properties`: URL начинается с `jdbc:h2:mem:`, пользователь `sa`, пустой пароль, `spring.jpa.hibernate.ddl-auto=create-drop`. Hibernate создаёт пустые таблицы; не добавляй начальные строки, `schema.sql` или `data.sql`.

Создай отдельные сущности гильдии и хранителя. Явно отобрази таблицы через `@Table` и колонки через `@Column`; связь — через `@ManyToOne` и `@JoinColumn(name = "guild_id", nullable = false)`. Обратную коллекцию `@OneToMany` не добавляй.

| Таблица | Колонки |
|---|---|
| `guilds` | `id BIGINT` — identity primary key; `name VARCHAR(40) NOT NULL` |
| `guild_keepers` | `id BIGINT` — identity primary key; `name VARCHAR(40) NOT NULL`; `level INTEGER NOT NULL`; `guild_id BIGINT NOT NULL` — внешний ключ на `guilds.id` |

Объяви и используй в репозитории хранителей производный метод с двумя условиями через `And`: ID связанной гильдии равен переданному, уровень хранителя **больше или равен** порогу. Укажи в названии метода сортировку по уровню по убыванию и затем по ID хранителя по возрастанию. Имена метода и Java-полей определяешь сам.

Не используй `@Query`, ручной SQL, `JdbcTemplate` или `findAll()` с фильтрацией/сортировкой в Java в приложении. Фильтр и порядок выполняет база через производный метод. Тесты используют JDBC только для независимой подготовки и проверки данных.

## HTTP-контракт

```text
GET /guilds/{guildId}/keepers?minLevel=5
```

- `guildId` — ID гильдии типа `long`. Параметр `minLevel` обязателен, его значение — неотрицательное число типа `int`.
- Существующая гильдия и корректный порог → `200 OK`, `Content-Type: application/json`, массив её хранителей с `level >= minLevel`.
- Порядок: сначала `level` по убыванию, при равных уровнях — собственный `id` хранителя по возрастанию.
- Каждый элемент содержит ровно `id`, `name`, `level`. Связанная гильдия в ответ не включается. Имена возвращаются без изменений.
- Нет подходящих хранителей или гильдия пуста → `200` и `[]`.
- Неизвестная гильдия при корректном пороге → `404`.
- Для существующей гильдии отсутствующий, пустой, состоящий только из пробелов, отрицательный, нецелый, нечисловой или выходящий за диапазон `int` параметр `minLevel` → `400`. Тело ошибки свободное.
- Допустимы пороги и уровни `0` и `Integer.MAX_VALUE`, ID больше `Integer.MAX_VALUE`, имена длиной 40 символов, кириллица и кавычки в имени.
- GET не меняет строки обеих таблиц, включая ответы `400` и `404`. Каждый новый запрос читает актуальные уровень, имя и принадлежность хранителей после изменения БД.
- База отклоняет хранителя с отсутствующей или несуществующей гильдией.

В приложении ты проверяешь неотрицательность порога и существование гильдии. Обязательность параметра и преобразование текста в число обрабатывает Spring MVC. Репозиторий гильдии проверяет наличие родительской записи; репозиторий хранителей возвращает список для DTO.

## Примеры

Пусть есть гильдия `3` и хранители: `id=40, name=Rin, level=9`; `id=30, name=Mira, level=5`; `id=20, name=Kai, level=5`; `id=10, name=Leo, level=4`. У другой гильдии есть хранитель уровня `99`.

1. `/guilds/3/keepers?minLevel=5` → `200`:

   ```json
   [{"id":40,"name":"Rin","level":9},{"id":20,"name":"Kai","level":5},{"id":30,"name":"Mira","level":5}]
   ```

2. `/guilds/3/keepers?minLevel=10` → `200` и `[]`; `/guilds/3/keepers?minLevel=-1` → `400`.
3. `/guilds/99/keepers?minLevel=0` → `404`, если гильдии `99` нет, даже если хранитель с ID `99` существует.
