## 1. Сценарий

Уведомление нужно двум обработчикам: один готовит его к показу клиенту, второй ведёт аудит. POST публикует **одну запись** в один topic. Каждый обработчик читает её в своей группе и сохраняет в своём хранилище. Это один Spring Boot-процесс и один Kafka-брокер; отдельные микросервисы создавать не нужно. Реальной отправки SMS/email здесь нет.

```text
POST → одна запись в bank.notifications.v2, 3 partitions
                 ├→ группа доставки → своё хранилище → GET delivery
                 └→ группа аудита    → своё хранилище → GET audit
```

Если двум listener назначить **одну группу**, Kafka распределит partitions между ними, а копия каждого события обоим не гарантируется. **Разные группы читают поток независимо**, поэтому одна запись доступна обоим обработчикам. Остановка группы доставки не должна останавливать аудит.

## 2. Partition и offset

### Зачем вообще разделять один тип сообщений

Представь только SMS: один topic `bank.sms.v1`, один и тот же метод отправки SMS. Допустим, приходят 30 запросов в секунду, а один последовательный consumer успевает обработать 10. Это условные числа для объяснения ограничения: необработанные запросы начинают накапливаться.

Чтобы разделить работу, можно запустить несколько consumer с одинаковой логикой **в одной группе**. Один метод listener в Java не означает одного работающего consumer: Spring может создать несколько consumer для него через `concurrency`, либо тот же код может работать в нескольких экземплярах приложения.

| Partitions у SMS-topic | Consumer в одной SMS-группе | Сколько consumer смогут читать параллельно |
|---:|---:|---:|
| 1 | 3 | 1; два останутся без назначенных partitions |
| 3 | 1 | 1; он читает все три partitions |
| 3 | 3 | До 3; можно распределить по одной partition каждому |

Именно так несколько partitions позволяют параллельно выполнять **одну и ту же работу для одного типа сообщений**. Для реального выигрыша сообщения должны поступать в разные partitions, например по ключам разных клиентов. Все сообщения одного ключа при неизменном числе partitions остаются в одной partition и сохраняют её порядок.

Тип потока в этом примере выделен topic `bank.sms.v1`. Группа `sms-senders` объединяет работников, отправляющих SMS. Номера partitions 0, 1, 2 сами по себе не означают SMS, email или аудит.

**Что происходит именно в №100:** при одном consumer в каждой группе три partitions не ускоряют обработку автоматически. Здесь проверяем доставку из всех трёх частей topic, независимость групп и настоящие метаданные записей. Прирост скорости и масштабирование consumer не являются критериями этой задачи; добавлять `concurrency=3` для её приёмки не требуется. Если нужен один consumer и он справляется с нагрузкой, одной partition достаточно.

### Как увидеть место конкретной записи

Partition — упорядоченная часть topic. Для этой практики topic содержит partitions `0`, `1`, `2`. Kafka присваивает записи позицию `offset` **внутри её partition**.

Пример возможного размещения конкретных уведомлений; номера ниже условные, фактические значения возвращает Kafka:

| Уведомление | clientId | Partition | Offset |
|---|---:|---:|---:|
| Карта готова | 17 | 0 | 5 |
| Поступление 500 рублей | 17 | 0 | 6 |
| Платёж принят | 42 | 2 | 5 |

В partition 0 уведомление «Карта готова» записано перед «Поступление 500 рублей». Уведомление другого клиента в partition 2 может иметь такой же offset 5: нумерация у partitions отдельная.

Offset не является общим ID уведомления. Позицию записи задаёт сочетание `topic + partition + offset`. Читая одну запись, обе группы видят одинаковые `partition` и `offset`. Прогресс чтения групп хранится отдельно; он не меняет метаданные самой записи. Ручное управление сохранёнными offsets здесь не требуется.

Передавай строковый `clientId` как key и не задавай partition вручную в приложении. При стандартной настройке producer одинаковый ключ попадает в одну partition, пока число partitions не меняется. Разные ключи могут попасть в одну partition. Порядок гарантируется внутри partition; общего порядка между всеми тремя partitions мы не требуем.

Сначала изучи [полный отдельный пример EXAMPLE.md](EXAMPLE.md). Он показывает две группы и получение метаданных из `ConsumerRecord` на настоящем Kafka.

## 3. Контракт Kafka

| Что | Обязательное значение |
|---|---|
| Topic | `bank.notifications.v2` |
| Число partitions | `3` |
| Replication factor | `1` |
| Группа доставки | `bank-notification-delivery-v1` |
| Группа аудита | `bank-notification-audit-v1` |
| Key | `clientId`, преобразованный в строку |
| Value | JSON-строка ровно с полями `clientId` и `text` |

Topic и group id — разные настройки. Имена групп выше фиксированы для проверки. Имена Java-классов, методов и listener id выбираешь сам.

- Объяви topic через `NewTopic`/`TopicBuilder`. Автосоздание topic на тестовом брокере отключено.
- Обе группы должны читать все три partitions. Для начала достаточно одного listener на каждую группу с обычной настройкой concurrency.
- Укажи разные `groupId` у двух `@KafkaListener` либо настрой их эквивалентно. Глобальное `spring.kafka.consumer.group-id` само по себе не задаёт две разные группы.
- Используй строковые serializer/deserializer для key/value, `auto-offset-reset=earliest`, producer `acks=all`.
- Адрес брокера получай из `spring.kafka.bootstrap-servers`; в тестах он подставляется автоматически.
- Получай настоящие метаданные записи, например через параметр `ConsumerRecord<String, String>`. Не вычисляй `partition` и `offset` по размеру очереди, счётчику запросов или порядку вызовов listener.
- POST только публикует. Каждый список пополняется только по вызову соответствующего listener. Использовать общий список для обоих обработчиков нельзя.

## 4. Контракт HTTP

### POST /api/notifications

```json
{"clientId":17,"text":"Карта готова"}
```

Ограничения из №99 сохраняются: обязательный положительный `clientId` типа `long`, обязательный `text` длиной 1–120 по `String.length()`, не пустой и не состоящий только из пробельных символов. Текст сохраняется без изменений, включая пробелы, кириллицу, кавычки и перевод строки.

Успех — `202 Accepted` с пустым телом после подтверждения публикации брокером. Ожидание результата отправки ограниченное, как в №99. Одна публикация на запрос; не отправляй отдельную запись для каждой группы. Некорректные значения, отсутствующее/пустое тело и сломанный JSON дают `400` без публикации. Формат тела ошибки свободный. Подтверждение отправки не означает завершения работы обоих listener.

### GET /api/notifications/delivery?clientId=17

### GET /api/notifications/audit?clientId=17

Оба endpoint возвращают `200` и JSON-массив следующего вида:

```json
[
  {"clientId":17,"text":"Карта готова","partition":1,"offset":8}
]
```

Значения `partition` и `offset` в примере условные: их определяет Kafka. Уведомление в обоих списках содержит одни и те же четыре поля и одинаковые метаданные одной записи.

- GET выбирает уведомления только указанного клиента из хранилища нужного обработчика; данные из другого списка не подмешиваются.
- Неизвестный клиент или ещё не обработанное событие: `[]`.
- Параметр `clientId` обязателен. Пустое значение, `0`, отрицательное число, нечисловая строка и выход за диапазон `long` дают `400`.
- Для последовательных сообщений одного клиента сохраняй порядок offsets его partition. Между разными клиентами/partitions общий порядок не требуется.
- GET не удаляет записи. Возвращай отдельный список результата, а не изменяемую очередь напрямую.
- Оба хранилища существуют только в памяти текущего запуска и безопасны для одновременной записи listener и чтения HTTP-потоком. `ConcurrentLinkedQueue` из №99 подходит; имена компонентов и внутреннюю структуру выбираешь сам.

## 5. Три примера

1. Один корректный POST → `202` → после обработки одна запись с одинаковыми метаданными в `delivery` и `audit`. В Kafka опубликована одна запись.
2. Listener доставки временно остановлен тестом. POST всё равно публикует; аудит обрабатывает запись. В списке доставки для нового клиента пока `[]`. После запуска listener доставки событие появляется и там.
3. Независимый producer отправил корректные записи в partitions 0, 1 и 2. Обе группы должны получить каждую; GET показывает реальные метаданные. Поэтому обработчик, читающий только partition 0, условию не соответствует.

## 6. Что создать

Рабочие файлы приложения: `src/main/java/learning/task100/`. Настройки: `src/main/resources/`. Нужны HTTP-контроллер, входной DTO, публикация, объявление topic, два listener и два отдельных потокобезопасных хранилища с чтением по клиенту. Один сервис может управлять обоими хранилищами, либо можно разделить их; обязательного количества классов нет.

В DTO ответа добавляются `partition` типа `int` и `offset` типа `long`. В JSON, который публикуется в Kafka, их добавлять не нужно: метаданные берутся из полученного `ConsumerRecord`. Входной DTO и модель обработанного уведомления могут быть разными типами.

В корневом `pom.xml` уже есть нужные версии Spring Kafka, Testcontainers Kafka и управление зависимостями через BOM из №99. Новые зависимости для этого шага не нужны. Java остаётся 21. Сам создай конфигурацию: можно опираться на собственные настройки №99, заменив topic и назначив две разные группы. Если сохраняешь JDBC/JPA-зависимости прошлого курса, отключи ненужную `DataSourceAutoConfiguration`, как в №99.

Все тесты находятся в [BankKafkaGroupsTest.java](src/test/java/learning/task100/BankKafkaGroupsTest.java). Docker-контейнер, случайный адрес, независимые producer/consumer и временную остановку listener организует тестовый код тренера. Тесты не создают приложение или topic за тебя и не меняют его настройки сериализации и групп.
