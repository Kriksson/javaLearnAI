# Задача №36 — Схема заказов игроков

**Сложность:** начинающий SQL  
**Закрепляем:** моделирование сущностей, ограничения данных.  
**Новое:** SQL DDL, таблицы, первичный и внешний ключи, `UNIQUE`, `CHECK`, `NOT NULL`.

Игровой магазин должен хранить игроков и их заказы. Спроектируй схему в PostgreSQL.

## Материал для изучения

### Что создаёт SQL

Реляционная база хранит данные в таблицах: строка — одна сущность, столбец — её свойство. Команда `CREATE TABLE` описывает структуру таблицы, а точка с запятой завершает SQL-команду.

```sql
CREATE TABLE accounts (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    login VARCHAR(50) NOT NULL UNIQUE
);
```

`INTEGER` хранит целые числа, `VARCHAR(n)` — строку не длиннее `n` символов, `DATE` — календарную дату, а `DECIMAL(10, 2)` — точное число с двумя знаками после запятой. Для денег не используют `DOUBLE`: возможны ошибки округления.

### Ограничения данных

- `NOT NULL` — значение обязательно.
- `UNIQUE` — одинаковое значение нельзя повторить.
- `PRIMARY KEY` — уникальный идентификатор строки.
- `GENERATED BY DEFAULT AS IDENTITY` — базовый вариант автоувеличиваемого идентификатора PostgreSQL.
- `CHECK (условие)` — база отклонит строку, если условие ложно. Например: `CHECK (amount >= 0)`.

### Связь таблиц

Внешний ключ связывает запись из дочерней таблицы с существующей записью из родительской:

```sql
CREATE TABLE payments (
    account_id INTEGER NOT NULL REFERENCES accounts(id)
);
```

Здесь нельзя создать платёж для несуществующего `account_id`. Сначала создают родительскую таблицу (`accounts`), затем дочернюю (`payments`). В этой задаче роль родительской таблицы выполняют игроки, а дочерней — их заказы.

## Что сделать

Заполни файл `src/main/resources/learning/task036/schema.sql` двумя командами `CREATE TABLE`.

### Таблица `players`

| Поле | Тип и правило |
|---|---|
| `id` | целое число, первичный ключ; значение генерируется базой данных |
| `nickname` | строка, обязательна и уникальна |
| `level` | целое число, обязательно; от 1 до 100 включительно |

### Таблица `player_orders`

| Поле | Тип и правило |
|---|---|
| `id` | целое число, первичный ключ; значение генерируется базой данных |
| `player_id` | целое число, обязательно; внешний ключ на `players(id)` |
| `item_name` | строка, обязательна |
| `total_price` | число с двумя знаками после запятой, обязательно; не меньше 0 |
| `purchased_at` | дата, обязательна |

## Примеры

```sql
INSERT INTO players (nickname, level) VALUES ('Kira', 42);
INSERT INTO player_orders (player_id, item_name, total_price, purchased_at)
VALUES (1, 'Magic sword', 199.99, DATE '2026-09-23');
```

```sql
INSERT INTO players (nickname, level) VALUES ('Kira', 10);
-- Ошибка: nickname уже занят.
```

```sql
INSERT INTO player_orders (player_id, item_name, total_price, purchased_at)
VALUES (999, 'Potion', 10.00, DATE '2026-09-23');
-- Ошибка: игрока с id 999 нет.
```

## Ограничения и готовность

- Не меняй имена таблиц и полей.
- Не добавляй Java-классы и зависимости: H2 добавлен только для автоматической проверки SQL.
- В `schema.sql` должны быть только SQL-команды и комментарии.
- Тесты должны пройти: они проверяют структуру, уникальность никнейма, диапазон уровня, цену и внешний ключ.
