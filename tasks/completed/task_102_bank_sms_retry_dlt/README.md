# Задача №102 — Банк: повторная отправка SMS и DLT

**Сложность:** базовая интеграционная, следующий шаг после №101. **Статус:** решена и архивирована 24.10.2026. Подтверждённый прогресс — **102** задачи. Все **43 теста** прошли с настоящим Kafka и локальным HTTP-шлюзом, без ошибок и пропусков.

**Формат:** приложение создаёшь ты в `learning.task102`. За основу можно взять своё архивное решение №101. Все тесты, Kafka и управляемый HTTP-шлюз готовит тренер; самостоятельные тесты не требуются.

**Закрепляем:** KafkaTemplate, JSON с ключом клиента, ConsumerRecord, три consumer одной группы, синхронный HTTP-вызов, таймауты, потокобезопасное хранение и валидацию API.

**Новое:** ограниченные повторы обработки через `DefaultErrorHandler` / `FixedBackOff`; перенос исчерпавшей попытки записи в отдельный topic через `DeadLetterPublishingRecoverer`.

## 1. Практическая проблема

В №101 шлюз возвращал успешный ответ. Теперь представь, что SMS «Карта готова» дошло до шлюза, но шлюз ответил `503 Service Unavailable`. Через короткое время он может восстановиться. Разумно попробовать снова.

В текущем решении №101 проверка успешного статуса только добавляет результат в очередь при `2xx`. При `503` метод просто заканчивается. Для контейнера listener это обычное завершение метода: исключения не было, поэтому повторная обработка не запрашивалась.

Следующий шаг — **сообщить контейнеру об ошибке через исключение**. Если из метода сервиса исключение выходит наружу через listener, настроенный обработчик ошибок решает, повторить вызов или завершить попытки. Если поймать исключение, записать его в лог и нормально вернуться, обработчик ошибок его не получит.

Но бесконечно повторять одно неисправимое SMS тоже нельзя: следующие сообщения той же partition будут ждать. После ограниченного числа попыток сохраняем исходное событие отдельно и продолжаем чтение основной partition.

**DLT — dead-letter topic:** обычный Kafka topic, куда приложение отправляет запись после исчерпания попыток. Он нужен для последующего разбора и управляемой повторной обработки. Сам факт появления в DLT не означает, что SMS доставлено.

## 2. Три конкретных сценария

| Ответы шлюза для одной записи | Что должно произойти |
|---|---|
| `204` | Один HTTP-вызов; добавить результат в хранилище; DLT пуст |
| `503 → 503 → 204` | Три HTTP-вызова для той же Kafka-записи; добавить результат один раз после успеха; DLT пуст |
| `503 → 503 → 503` | Три HTTP-вызова; отправить исходную запись в DLT; в успешном хранилище её нет; перейти к следующей записи partition |

**Три попытки — первая обработка и два повтора.** Счётчик относится к конкретной Kafka-записи. Для следующей записи снова доступен весь бюджет.

В этой практике используем короткую фиксированную задержку повторов **100 мс**. Это учебное значение; проверка не измеряет точность таймера. Время HTTP-вызова в эту задержку не входит.

```text
POST API → одна публикация в Kafka → подтверждение брокера → 202
                       ↓
                 listener → сервис → POST шлюзу
                                ↓
                    2xx → успешное хранилище → GET
                                ↓ при ошибке
                   исключение выходит из listener
                                ↓
                    DefaultErrorHandler
                      ├─ попытки есть → снова обработать ту же запись
                      └─ попытки закончились → recoverer → DLT
```

Повторная обработка сохраняет исходные `topic`, `partition`, `offset`, `key` и `value`. Новая публикация исходящего POST в основной topic для каждого повтора не нужна.

Сначала прочитай [отдельный работающий пример](EXAMPLE.md). В нём шлюз печати этикеток посылок сначала отказывает, а затем либо восстанавливается, либо запись отправляется в topic ошибок. Пример использует те же Spring Kafka, HTTP и Testcontainers, но не содержит банковского API.

## 3. Контракт Kafka

| Параметр | Значение |
|---|---|
| Основной topic | `bank.sms.v1` |
| Topic ошибок | `bank.sms.v1.DLT` |
| Partitions / replicas каждого topic | `3` / `1` |
| Consumer group основного listener | `bank-sms-senders-v1` |
| Consumer основного listener | `3`, стандартный listener concurrency |
| Key основной записи и её копии в DLT | Числовой `clientId`, преобразованный в строку |
| Value | JSON-строка ровно с полями `clientId` и `text` |

Оба topic объявляются приложением через `NewTopic`/`TopicBuilder`. DLT имеет три partitions, чтобы запись из любой основной partition можно было отправить в DLT с тем же номером partition.

Для основного producer сохраняются строковые serializer/deserializer, `acks=all`, `auto-offset-reset=earliest` и адрес из `spring.kafka.bootstrap-servers`. Основная публикация распределяется по key без ручного указания partition. Тестовый producer явно задаёт partitions только для управляемых сценариев.

SMS-listener подписан на основной topic. В этой задаче DLT читает независимый consumer тестов; дополнительный listener для отправки SMS из DLT не нужен.

## 4. Обработка ошибки и повторы

Используй стандартный контейнерный **`DefaultErrorHandler`**, **`FixedBackOff(100L, 2L)`** и **`DeadLetterPublishingRecoverer`**. `2L` задаёт число повторов после первой попытки. Ручной цикл повторов в сервисе, общий изменяемый счётчик, `@RetryableTopic` и фоновые задачи здесь не используются.

В Spring Boot обработчик можно объявить bean: Boot подключит `CommonErrorHandler` к автоматически созданной listener factory. Если создаёшь свою factory, сам подключи обработчик через `setCommonErrorHandler`. Атрибут `@KafkaListener(errorHandler=...)` относится к другому виду обработчиков; он не заменяет эту настройку контейнера.

На каждый вызов обработки:

1. Прочитай JSON исходной записи.
2. Выполни один синхронный HTTP POST к шлюзу.
3. При `2xx` добавь в потокобезопасное хранилище результат с исходными `partition` и `offset`.
4. При неуспешном HTTP-статусе выбрось исключение, например `IOException`, и передай его наружу через listener. Сетевые ошибки тоже передаются наружу. Запись в успешное хранилище на ошибочной попытке не добавляется.
5. Повторы и перенос в DLT выполняет настроенный обработчик контейнера.

Учебный шлюз использует `204` и `503`. Политику разделения всех возможных HTTP-кодов, смену типов ошибок между попытками и восстановление после падения процесса в этой задаче не разрабатываем.

Один готовый HttpClient переиспользуется. HttpRequest и его builder создаются для каждого вызова. Сохраняются ограниченные ожидания публикации, подключения и HTTP-ответа; подходящие учебные значения — 10, 2 и 10 секунд соответственно.

Блокирующие повторы задерживают обработку следующих записей этой partition. При трёх consumer остальные partitions могут продвигаться независимо. После успеха либо успешной публикации неисправимой записи в DLT чтение её partition продолжается.

## 5. Что должно попасть в DLT

После третьего ответа `503` публикуется **одна** запись:

- topic — `bank.sms.v1.DLT`;
- partition — номер исходной partition;
- key — исходный key;
- value — исходная JSON-строка без обёртки и без добавления полей ошибки в JSON;
- стандартные headers recoverer содержат сведения об источнике и исключении.

Используй явное правило выбора topic и partition в recoverer, как в примере. Так имя `.DLT` задаётся твоим контрактом, а не зависит от значения по умолчанию в библиотеке.

Headers — дополнительные метаданные рядом с key и value. Для этой задачи важны:

| Константа KafkaHeaders | Смысл |
|---|---|
| `DLT_ORIGINAL_TOPIC` | Откуда прочитана неудачная запись |
| `DLT_ORIGINAL_PARTITION` | Её исходная partition |
| `DLT_ORIGINAL_OFFSET` | Её исходный offset |
| `DLT_ORIGINAL_CONSUMER_GROUP` | Группа, в которой произошла ошибка |
| `DLT_EXCEPTION_FQCN`, `DLT_EXCEPTION_MESSAGE` | Тип и сообщение исключения |

Эти headers создаёт стандартный recoverer; вручную собирать их не требуется. В `ConsumerRecord` значения headers представлены массивами байтов; тесты декодируют строки в UTF-8, partition как `int`, offset как `long`.

**У записи в DLT свой новый offset.** Он относится к DLT. Исходный offset хранится отдельно в `DLT_ORIGINAL_OFFSET`; сравнивать их как одно значение нельзя.

Включи у recoverer `setFailIfSendResultIsError(true)`: ошибка публикации в DLT должна выходить наружу. В тестах брокер работает штатно; сценарий недоступности брокера во время recovery — отдельная практика.

## 6. Контракт HTTP

### Входящий POST /api/sms-requests

```json
{"clientId":17,"text":"Карта готова"}
```

- `clientId` — обязательное целое `long`, от 1 до `Long.MAX_VALUE`.
- `text` — обязательная непустая строка, не только пробелы; длина 1–120 по `String.length()`. Текст сохраняется без изменений.
- Один корректный запрос создаёт одну основную Kafka-запись и возвращает `202` с пустым телом после подтверждения брокера.
- `202` означает принятую публикацию. Он возвращается и тогда, когда последующая обработка завершится переносом в DLT. Входящий POST не ждёт результата шлюза или всех повторов.
- Некорректные/отсутствующие поля, пустое/отсутствующее тело и сломанный JSON дают `400` без публикации. Формат ошибки свободный.

### Исходящий POST к шлюзу

Полный URL берётся из **`bank.sms-gateway-url`**. Он содержит случайный порт и путь `/gateway/sms`. Используй его целиком.

На каждую попытку отправляй `Content-Type: application/json` и исходные `clientId` / `text`. При `204` обработка успешна. При `503` она завершается исключением. Сервис не выбирает ответы шлюза и не считает попытки сам — план ответов задаёт тестовая инфраструктура.

### GET /api/sms-requests?clientId=17

```json
[
  {"clientId":17,"text":"Карта готова","partition":1,"offset":8}
]
```

Значения метаданных в примере условные; используй реальные метаданные основной записи Kafka.

- `200` и список только успешно обработанных уведомлений клиента. До успешного ответа шлюза список для его записи пуст. Записи, отправленные в DLT, в список не попадают.
- После нескольких неудач и последующего успеха появляется одна запись, с исходным offset. Повторы сами по себе не добавляют элементы.
- Неизвестный клиент получает `[]`. GET сохраняет данные и возвращает отдельный список.
- Порядок успешно обработанных записей одной partition сохраняется. После неисправимой записи следующие могут быть успешно обработаны.
- `clientId` обязателен. Отсутствующее/пустое значение, ноль, отрицательное число, буквы и переполнение `long` дают `400`.
- `clientId`, `partition` и `offset` в ответе — числа. Поле называется `partition` в единственном числе.

## 7. Границы этой практики

В управляемых сценариях ответ `503` означает отказ шлюза до отправки SMS. Повторы в реальных интеграциях могут приводить к дублям: при сетевом таймауте внешняя операция могла уже выполниться. Защита от повторного бизнес-действия, идентификатор события и идемпотентность будут следующим отдельным шагом. Здесь не обещаем exactly-once отправку SMS.

Также пока не нужны БД, сохранение списка после перезапуска, HTTP API для DLT, ручной commit/seek, Kafka-транзакции, собственные ExecutorService, параллельные Stream или `HttpClient.sendAsync()`.
