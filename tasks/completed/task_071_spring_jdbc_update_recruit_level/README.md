# Задача №71 — Изменение уровня рекрута через Spring JDBC

**Сложность:** базовая. Один новый SQL-приём и один endpoint.

**Формат:** спроектируй и собери приложение с нуля. Сам создай Java-файлы, настройки и SQL-схему в пакете `learning.task071`; используй текущий Maven-проект и уже подключённые зависимости.

**Закрепи:** Spring Boot REST API, Bean Validation, H2, параметризованные SQL-запросы и интеграционные проверки через MockMvc.

**Новое:** `UPDATE ... WHERE` через `JdbcTemplate.update` и обработка числа изменённых строк.

## Сценарий

Наставник гильдии меняет уровень существующего рекрута. Запрос должен обновить только его уровень и не создавать запись, если ID не найден.

Создай таблицу `guild_recruits`:

```sql
CREATE TABLE guild_recruits (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(30) NOT NULL,
    level INTEGER NOT NULL
);
```

Для H2 настрой источник данных в `src/main/resources/application.properties` и запуск `schema.sql` при старте.

## Новый приём: UPDATE и число изменённых строк

В отдельном приложении кузницы можно менять прочность предмета. Метод `JdbcTemplate.update` возвращает число строк, подходивших под `WHERE`:

```java
public int updateDurability(long itemId, int durability) {
    return jdbc.update(
            "UPDATE forge_items SET durability = ? WHERE id = ?",
            durability,
            itemId
    );
}
```

`?` для прочности получает `durability`, второй `?` — `itemId`; JDBC связывает значения отдельно от SQL-текста. Возвращённое `1` означает, что строка найдена и изменена, а `0` — что такого предмета нет.

Внешний слой использует этот результат, чтобы вернуть верный HTTP-статус:

```java
if (repository.updateDurability(id, request.durability()) == 0) {
    return ResponseEntity.notFound().build();
}
return ResponseEntity.noContent().build();
```

Путь данных в примере: JSON `{"durability":80}` → Spring MVC создаёт объект запроса → `@Valid` проверяет диапазон → контроллер передаёт ID и значение в репозиторий → параметризованный SQL обновляет строку → число изменённых строк определяет ответ `204` или `404`. В коде тестов кузницы таких нет: в этой задаче ты напишешь проверки своего API.

Используй те же роли в своём приложении, но сам выбери имена файлов, классов и методов. Пример относится к другой таблице и не является готовой реализацией задачи.

## HTTP-контракт

```text
PUT /guild/recruits/{id}
Content-Type: application/json
```

Тело содержит только поле `level` — целое JSON-число от `1` до `100` включительно. `id` — целое число типа `long` в пути. Проверки дробных JSON-чисел отдельно не настраивай.

- Если запись с ID существует, измени только её `level`, оставив `id` и `name` без изменений. Верни `204 No Content` без тела.
- Если числового `long` ID нет в таблице, верни `404 Not Found` без тела. Новая строка не появляется.
- Если ID в пути не преобразуется в `long` или выходит за диапазон `long`, Spring MVC возвращает `400 Bad Request`.
- При отсутствующем, пустом, повреждённом или невалидном JSON верни `400 Bad Request`. Таблица при этом не меняется.
- Повтор одинакового валидного `PUT` возвращает `204`; значение в таблице остаётся тем же.

Пример: при записи `id=12, name="Лира", level=25` запрос с телом `{"level":40}` возвращает `204`, а строка становится `id=12, name="Лира", level=40`.
