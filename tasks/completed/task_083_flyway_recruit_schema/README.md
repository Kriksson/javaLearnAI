# Задача №83 — Первая миграция Flyway

**Сложность: базовая. Схему PostgreSQL создаёт SQL-миграция.**

Собери приложение с нуля в пакете `learning.task083`. Снова нужны создание рекрута и чтение по ID: небольшой знакомый API позволит сосредоточиться на управлении схемой.

Закрепляем: PostgreSQL, внешний конфиг, SQL `CREATE TABLE`, ограничения, JPA, identity ID, DTO, валидацию и статусы HTTP.

Новые понятия: **версионированная миграция Flyway** и **проверка соответствия схемы сущностям через Hibernate `validate`**.

## Зачем нужна миграция

В №82 Hibernate создавал таблицу по сущности через `ddl-auto=update`. Теперь ты явно описываешь схему SQL-файлом и сохраняешь этот файл вместе с проектом. На пустой схеме Flyway выполняет миграцию, записывает результат в `flyway_schema_history`; последующие запуски видят применённую версию и не выполняют её заново. История также содержит checksum — контрольную сумму файла. Применённую версию не редактируют: будущие изменения оформляют следующим файлом V2. В этой задаче нужна только V1. [Версионированные миграции Flyway](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/versioned-migrations).

Название `V1__create_books.sql` читается так: `V` — версионированная миграция, `1` — версия, **два** подчёркивания отделяют описание, `create_books` — описание, `.sql` — SQL-файл. Стандартное место — `src/main/resources/db/migration/`. Spring Boot запускает Flyway автоматически при старте, если подключены необходимые зависимости. [Flyway в Spring Boot](https://docs.spring.io/spring-boot/3.5/how-to/data-initialization.html#howto.data-initialization.migration-tool.flyway).

### Отдельный работающий пример: таблица книг

Для отдельного Spring Boot приложения с PostgreSQL и Flyway файл `src/main/resources/db/migration/V1__create_books.sql` может содержать:

```sql
CREATE TABLE books (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(80) NOT NULL,
    pages INTEGER NOT NULL CHECK (pages >= 1)
);
```

- `CREATE TABLE` создаёт таблицу при применении V1 к пустой схеме.
- `GENERATED BY DEFAULT AS IDENTITY` выдаёт ID при вставке без ID; `PRIMARY KEY` обеспечивает уникальность.
- `VARCHAR(80) NOT NULL` ограничивает длину заголовка и запрещает `NULL`.
- `CHECK` отклоняет недопустимое число страниц, даже если запись делает другой клиент базы.

Этот пример остаётся в учебном материале. Таблицу рекрутов и её SQL проектируешь сам.

## Hibernate validate

Для отдельного приложения книг с JPA-сущностью, отображённой на `books`, настройка выглядит так:

```properties
spring.jpa.hibernate.ddl-auto=validate
```

Hibernate проверяет, что нужные таблицы и колонки существуют и их типы совместимы с сущностями. Он не создаёт и не исправляет схему. Если сущность ожидает колонку `pages`, а в базе её нет, запуск завершится ошибкой проверки схемы. `validate` не заменяет SQL-ограничения или проверку входящего JSON. [Инициализация и проверка схемы](https://docs.spring.io/spring-boot/3.5/how-to/data-initialization.html#howto.data-initialization.using-hibernate).

Полный путь данных и запуска:

```text
Переменные окружения → DataSource PostgreSQL
                     → Flyway находит V1 → выполняет SQL → записывает историю
                     → Hibernate проверяет схему → приложение готово
POST JSON → Spring/Jackson создаёт DTO → твоя валидация
          → JpaRepository.save → Hibernate INSERT → PostgreSQL выдаёт ID
          → DTO ответа и Location
```

Проверки имени и уровня на входе пишешь ты. Ограничения SQL также пишешь ты в миграции: у HTTP и базы разные точки входа.

## Зависимости и подключение

Самостоятельно добавь `org.flywaydb:flyway-core` и модуль `org.flywaydb:flyway-database-postgresql` одной версии. Для Spring Boot 3.5.16 ориентир — **11.7.2**. В текущем `pom.xml` нет общего Spring Boot BOM, поэтому версия этих зависимостей должна быть указана явно либо управляться подключённым тобой BOM. PostgreSQL-драйвер и остальные необходимые зависимости также проверяешь сам. Java остаётся 21. [Версии зависимостей Spring Boot](https://docs.spring.io/spring-boot/3.5/appendix/dependency-versions/coordinates.html).

Вручную создай `src/main/resources/application.properties`:

| Свойство | Требуемое значение |
|---|---|
| `spring.datasource.url` | `${COURSE_PG_URL}` без значения по умолчанию |
| `spring.datasource.username` | `${COURSE_PG_USER}` |
| `spring.datasource.password` | `${COURSE_PG_PASSWORD}` |
| `spring.jpa.hibernate.ddl-auto` | `validate` |
| `spring.jpa.open-in-view` | `false` |

Flyway использует тот же `DataSource`, что JPA. Оставь стандартные расположение миграций и название истории, не задавай отдельное подключение Flyway, фиксированную схему, `baseline-on-migrate` или очистку схемы при запуске. `schema.sql`, `data.sql`, `import.sql` и создание таблиц из Java здесь не используются. Миграцию запускает стандартная автоконфигурация Spring Boot.

Используй **новую пустую учебную базу** для обычного запуска: в базе №82 таблица уже создана Hibernate без истории Flyway. Для этой практики не нужно переводить существующую базу на миграции; это отдельный сценарий. Пользователь PostgreSQL должен иметь права создания таблиц и схем.

## Схема и миграция

Самостоятельно создай **ровно одну** миграцию:

`src/main/resources/db/migration/V1__create_recruits.sql`.

Она создаёт таблицу `recruits` с ровно тремя колонками:

| Колонка | Требования |
|---|---|
| `id` | `BIGINT`, `GENERATED BY DEFAULT AS IDENTITY`, единственный primary key |
| `name` | `VARCHAR(40) NOT NULL` |
| `level` | `INTEGER NOT NULL`, SQL-ограничение `CHECK (level >= 0)` |

Не добавляй начальные записи или другие таблицы приложения. `flyway_schema_history` создаёт сам Flyway. Не указывай `public` или другое имя схемы в SQL и `@Table`: используется текущая схема подключения.

Создай одну JPA-сущность с явными именами таблицы и колонок, ID типа `Long` и `GenerationType.IDENTITY`. Доступ к рекрутам — через Spring Data JPA `save` / `findById`. Имена внутренних классов и методов выбираешь сам.

## HTTP-контракт

### POST /recruits

Входной JSON: `{"name":"Mira","level":3}`.

- `name` обязателен, не `null`, не пуст и не состоит только из пробелов; максимум 40 символов. Сохраняй допустимое имя точно: кириллицу, кавычки и пробелы вокруг непустого имени.
- `level` обязателен и не `null`, от 0 до `Integer.MAX_VALUE`. Входная модель должна различать отсутствие уровня и ноль.
- Корректный запрос → `201 Created`, `Location: /recruits/{выданныйId}`, JSON с ровно `id`, `name`, `level`. ID положительный, настоящий, выданный PostgreSQL.
- Повтор одинакового POST создаёт ещё одну строку с другим ID; существующие строки не меняются.
- Отсутствующее тело, JSON `null`, отсутствующее или `null` поле, недопустимое имя, отрицательный уровень, число вне диапазона `int`, непреобразуемый уровень или повреждённый JSON → `400` без новой записи и изменения прежних. Формат ошибки свободный.

### GET /recruits/{id}

- ID имеет диапазон `long`, включая значения больше `Integer.MAX_VALUE`.
- Существующая строка → `200`, JSON с ровно `id`, `name`, `level`; неизвестный или удалённый ID → `404`.
- Читай актуальные значения базы после внешнего изменения или удаления строки. GET не меняет данные.
- Используй DTO для HTTP-ответа.

### Запуск и сохранность

- Первый запуск на пустой схеме автоматически применяет V1 до проверки схемы Hibernate.
- История содержит одну успешно применённую SQL-миграцию версии `1` с именем `V1__create_recruits.sql` и checksum.
- После повторных запусков сохранённые рекруты доступны, а запись истории не меняется: V1 не выполняется повторно.
- База отклоняет `NULL` в имени/уровне, имя длиннее 40 символов и отрицательный уровень, в том числе при прямом SQL INSERT.
- Если после применения миграции убрать ожидаемую колонку `level`, следующий запуск должен упасть именно на проверке Hibernate и не восстановить колонку. Тест имитирует это только в своей временной схеме и затем возвращает колонку обратно.

## Примеры

1. Пустая схема → старт приложения → появились `recruits` и история V1. POST `{"name":"Mira","level":3}` → `201`, например `{"id":1,"name":"Mira","level":3}` и `Location: /recruits/1`.
2. Перезапуск с тем же подключением → в истории по-прежнему одна запись V1; GET `/recruits/1` возвращает сохранённого рекрута.
3. POST `{"name":"Mira","level":-1}` → `400`. Прямая SQL-вставка с уровнем `-1` также отклоняется базой благодаря CHECK.

## Файлы, ограничения и проверка

Сам создавай файлы приложения в `src/main/java/learning/task083/`: стартовый класс, сущность, репозиторий, DTO запроса/ответа и контроллер; сервис добавляй по необходимости. Каждый самостоятельный класс — отдельный файл. Конфигурацию, SQL-миграцию, зависимости и сборку тоже создаёшь сам.

Тесты тренера:

- `src/test/java/learning/task083/FlywayRecruitApiTest.java` — 8 интеграционных тестов и предварительные проверки конфигурации/схемы/истории;
- `src/test/java/learning/task083/PostgresTestDatabase.java` — изоляция в случайной схеме `task083_<идентификатор>`.

Тесты работают с настоящим PostgreSQL из `COURSE_PG_*`, создают и удаляют только свою схему. Таблицу в ней создаёт твоя миграция. Тесты меняют только параметры подключения, а `validate` и Flyway проверяются из конфигурации приложения. Они не зависят от выбранных тобой имён внутренних классов. Не используй H2, `JdbcTemplate`, `@Query`, ручные запросы или локальные коллекции для хранения в приложении; SQL допустим в миграции. Тесты независимо проверяют базу через JDBC.
